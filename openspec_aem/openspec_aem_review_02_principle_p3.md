## What OpenSpec asserts about this principle

OpenSpec asserts that architecture is a *spec-before-code* convention layered on top of a markdown-driven proposal/spec/delta workflow. The README declares the philosophy as `"→ fluid not rigid"` and `"easy not complex"` (`OpenSpec/README.md` lines 28–34). `OpenSpec/docs/concepts.md` line 586 states `"Dependencies are enablers, not gates. They show what's possible to create, not what you must create next."`. The only architecture-adjacent control surface is markdown structural validation in `OpenSpec/src/core/validation/validator.ts` (459 lines, Zod-based) plus an opt-in `--strict` validation flag (`OpenSpec/docs/cli.md` line 434) and `openspec/specs/` versus `openspec/changes/` directory separation (`OpenSpec/openspec/`). OpenSpec does not assert any runtime policy enforcement, sandboxing, repository gating, type contract checking, lint integration, ownership map enforcement, or CI guardrails for the agents that generate or apply its artefacts.

## Blast-Radius Test

### 1. Single-agent failure — silent wrong output

A single coding agent driven by `/opsx:propose` or `/opsx:apply` (`OpenSpec/docs/commands.md` lines 320–488) produces a proposal, design, tasks, and delta specs that are syntactically valid markdown matching the `SpecSchema`/`ChangeSchema` Zod parsers in `OpenSpec/src/core/validation/validator.ts`, but semantically wrong (e.g., a 2FA delta whose scenario quietly removes idempotency guarantees, or a payments delta that re-classifies a major-model change as minor). Propagation path:

1. Agent writes `openspec/changes/<change>/proposal.md`, `design.md`, `tasks.md`, and delta `spec.md`. No human review is required by the tool — `OpenSpec/docs/commands.md` line 380 states `"Warnings don't block archive but indicate potential issues"` and line 488 states `"Archive won't block on incomplete tasks, but will warn"`.
2. `openspec validate` (default mode) checks structural shape only (purpose length, requirement text length, scenario presence — `OpenSpec/src/core/validation/constants.ts`). It does not check semantic correctness, ownership, blast-radius, or domain invariants. `--strict` (`OpenSpec/docs/cli.md` line 434, opt-in) tightens markdown shape rules; it adds no runtime or domain enforcement.
3. `/opsx:archive` (`OpenSpec/docs/commands.md` line 511 `"Validates each change before archiving"`) runs the same structural validator and merges `ADDED/MODIFIED/REMOVED` deltas into `openspec/specs/**/*.md` (`OpenSpec/docs/concepts.md` lines 521–527). Because deltas are the source of truth after merge, the wrong requirement now becomes ground-truth specification for all future changes (`OpenSpec/docs/concepts.md` line 50: `"when you archive a change, its deltas merge cleanly into the source of truth"`).
4. Downstream coding agents reading `openspec/specs/` retrieve the corrupted requirement and propagate it into application code, evaluations, and any test suite generated from spec scenarios. There is no second-layer check anywhere in OpenSpec that would catch the drift; the framework's scope ends at markdown.

Maximum blast radius: full-corpus, persistent, retroactive. The corrupted requirement contaminates every subsequent change because deltas merge without a defence-in-depth verification layer. For Allianz pricing, underwriting, claims, and Solvency II internal-model code, this is unbounded — OpenSpec exits scope before any code, deployment, or evaluation gate exists.

### 2. Isolation mechanisms

| Mechanism | Enforcement | Failure class caught |
| --- | --- | --- |
| `openspec/specs/` vs `openspec/changes/` directory separation (`OpenSpec/docs/concepts.md` lines 31–43) | Convention (filesystem layout) | Structural — prevents accidental edits to source-of-truth specs while a change is in flight; catches no semantic, ownership, or blast-radius failure |
| Zod-schema markdown validation in `OpenSpec/src/core/validation/validator.ts` | Runtime, but only when `openspec validate` is invoked | Structural — missing `## Purpose`, missing scenarios, malformed requirement headers |
| `--strict` validation flag (`OpenSpec/docs/cli.md` line 434) | Opt-in, runtime only when explicitly passed | Structural — additional shape rules |
| Schema dependency DAG (`OpenSpec/docs/concepts.md` lines 540–586) | Convention — `"Dependencies are enablers, not gates"` (line 586) | None — the docs explicitly state these are not gates |
| `/opsx:verify` (`OpenSpec/docs/commands.md` lines 320–340) | Advisory, agent-driven; line 336: `"Does not block archive, but surfaces issues"` | Semantic gap-detection at advisory level — no enforcement |
| Archive merge step (`OpenSpec/src/core/archive.ts`) | Runtime, structural | Structural — applies deltas; performs no domain-ownership, blast-radius, or policy check |
| Telemetry (`OpenSpec/src/telemetry/`) | Runtime, anonymous command counts only (README lines 185–192) | None — observational only, opt-out by default settings |

No mechanism is enforced at the runtime where agent actions land (filesystem write, git commit, CI run, deployment). No mechanism inspects content semantics. No mechanism enforces domain ownership boundaries, repository gates, API rate limits, type contracts, lint rules, or data-access policies. The schema dependency graph (`OpenSpec/openspec/schemas/spec-driven/schema.yaml` referenced in `concepts.md` line 544) is documented as advisory only.

### 3. Verdict

OpenSpec's architecture is defence-in-line, not defence-in-depth. The only layer is structural markdown validation. P3's minimum bar in `manifesto-principles.md` line 147–148 — `"If a boundary is described but not enforced at runtime with automated detection and recovery, it is not architecture — it is documentation."` — is not met: every boundary OpenSpec describes (proposal vs spec, schema dependency, change scope, archive cadence) is enforced as filesystem convention or opt-in advisory validation, not as runtime policy with automated detection and recovery. The manifesto's three-layer model — wrappers (P3) + verification (P8) + observability (P9) — collapses to a single advisory layer in OpenSpec.

## What works

- `OpenSpec/openspec/specs/` versus `openspec/changes/` directory separation (`OpenSpec/docs/concepts.md` lines 31–43) gives a single deterministic source of truth and an isolated change workspace, reducing accidental edits to current specs.
- `OpenSpec/src/core/validation/validator.ts` (459 lines, Zod-based via `SpecSchema` and `ChangeSchema` in `OpenSpec/src/core/schemas/`) provides machine-checkable structural validation for spec markdown — a real, enforced shape contract on the artefact.
- The delta-spec format (`ADDED`/`MODIFIED`/`REMOVED` Requirements documented in `OpenSpec/docs/concepts.md` lines 521–527) is parseable by `OpenSpec/src/core/parsers/requirement-blocks.ts`, allowing automated diff inspection of proposed changes before merge — a structural boundary on what a change can claim to do.
- The `openspec validate --strict --all --concurrency 12` invocation (`OpenSpec/docs/cli.md` lines 434, 455) is wireable into CI to enforce structural conformity at PR time — the only runtime-enforceable lever OpenSpec offers, and only for markdown shape.
- `/opsx:verify` (`OpenSpec/docs/commands.md` lines 320–340; `OpenSpec/docs/workflows.md` lines 236–271) advises on three dimensions of implementation-vs-spec drift — not enforcement, but a documented advisory check the user can invoke.
- The archive step writes to `openspec/changes/archive/<date>-<slug>/` (`OpenSpec/docs/concepts.md` lines 656–671) preserving full proposal/design/tasks/delta artefacts as an immutable historical record under git — a documentation-grade audit trail for spec evolution.
- The `openspec/schemas/spec-driven/schema.yaml` artefact graph (`OpenSpec/docs/concepts.md` lines 540–586) declares artefact dependencies machine-readably, allowing tools to detect missing artefacts even though the framework chooses not to gate on them.

## Where it fails the manifesto's bar

- `manifesto-principles.md` lines 130–132: `"Encode boundaries as machine-enforced policies: repository gates, type contracts, lint rules, domain ownership maps, CI checks."` — OpenSpec encodes zero of these. There is no domain ownership map (`openspec/specs/<domain>/spec.md` is convention only — `OpenSpec/docs/concepts.md` lines 197–206 describe domain folders as `"logical groupings"`), no lint integration, no type contract beyond markdown shape, no CI gate beyond an opt-in `validate` invocation. **Allianz exposure:** Solvency II Article 121 (statistical quality and validation standards for internal models) requires ownership and change governance enforced at policy level, not advised at convention level.
- `manifesto-principles.md` lines 134–137: `"Do not rely on an LLM's system prompt to enforce your business rules. Build deterministic infrastructure wrappers around your probabilistic AI. Enforce permissions, repository gates, API rate limits, and data access at the system level."` — OpenSpec's `OpenSpec/src/prompts/` and `OpenSpec/src/commands/` ship deterministic prompt scaffolding for slash commands but **wrap no execution surface**. The agent that drives `/opsx:apply` writes files, runs tools, and modifies git history with no permission, rate limit, or access control imposed by OpenSpec itself. **Allianz exposure:** DORA Articles 6 and 8 (ICT risk management framework, identification and protection of critical functions) require system-level enforcement of agent action boundaries on critical insurance-IT functions; convention-level enforcement does not satisfy DORA.
- `manifesto-principles.md` lines 141–145: `"Deterministic wrappers catch structural failures … verification catches semantic errors (Principle 8), and observability catches behavioral drift (Principle 9). No single layer catches everything. All three must hold."` — OpenSpec provides only a partial structural layer (markdown shape). It does not produce or require runtime traces, evaluation reports, deployment IDs, or rollback artefacts; `OpenSpec/src/telemetry/` records anonymous command counts only (`README.md` lines 185–192). All three layers fail to hold. **Allianz exposure:** EU AI Act Article 9 (risk management system) and Article 15 (accuracy, robustness, cybersecurity) for high-risk insurance AI systems require all three layers operational; OpenSpec satisfies one structural layer at convention level.
- `manifesto-principles.md` lines 147–148 (P3 minimum bar): `"If a boundary is described but not enforced at runtime with automated detection and recovery, it is not architecture — it is documentation."` — every OpenSpec boundary is documented (`docs/concepts.md`, `docs/workflows.md`, `docs/opsx.md`); none is enforced at runtime with automated detection and recovery. `OpenSpec/docs/commands.md` line 336 (`"Does not block archive, but surfaces issues"`) and line 488 (`"Archive won't block on incomplete tasks, but will warn"`) are explicit admissions. **Allianz exposure:** SR 11-7 §IV (model implementation, use, and validation) requires policy boundaries enforced at runtime for material models; OpenSpec is documentation, not architecture, by its own admission.
- `manifesto-principles.md` lines 137–138: `"Expect the boundary to be tested. Design for what happens when it is crossed."` — OpenSpec specifies no recovery, kill-switch, rollback, or boundary-violation alert. The archive merge in `OpenSpec/src/core/archive.ts` is one-way; there is no documented procedure for reverting a merged delta that introduced a corrupted requirement, beyond raising another change. **Allianz exposure:** DORA Article 11 (response and recovery) and EU AI Act Article 15 require pre-engineered recovery from boundary failures; OpenSpec leaves recovery to ad-hoc spec authoring.
- `OpenSpec/docs/concepts.md` line 586: `"Dependencies are enablers, not gates. They show what's possible to create, not what you must create next."` — this is the framework's stated design choice and directly contradicts P3's enforcement minimum bar. Permitting `tasks.md` without `specs/*.md` (line 586 example) means an agent can implement against an implicit spec that was never written, producing semantically valid markdown for a contract that does not exist. **Allianz exposure:** Solvency II Article 124 (documentation standards for internal models) and EIOPA AI Guidelines 2021 Principle 4 (documentation and audit trail) require derivation traceability between intent → spec → implementation; OpenSpec's enabler-not-gate stance breaks the chain.
- `manifesto-principles.md` line 4 (companion `companion/principles.md` line 256): `"a concrete implementation of architecture as defense-in-depth"` describes the pattern manifesto-aligned frameworks must instantiate. OpenSpec's `/opsx:verify` is advisory (`OpenSpec/docs/commands.md` line 336), `/opsx:archive` is non-blocking on warnings (line 380), and there is no second or third defensive layer. The framework is single-layer-by-design. **Allianz exposure:** GDPR Article 22 (automated decisions) and Article 25 (data protection by design) require multi-layer defence for processing affecting data subjects; one advisory layer does not satisfy Article 25.

## Allianz-specific implications

- **Solvency II Article 121 (statistical quality, calibration, validation standards) and Article 124 (documentation standards):** OpenSpec's specs are markdown-validated but the framework does not enforce that internal-model specifications carry actuarial sign-off, calibration evidence, or validation function approval. Allianz operating an OpenSpec-driven workflow on internal-model changes must layer Solvency II IMAP gates as external CI checks, model-ownership enforcement, and validator approval workflows that OpenSpec itself does not provide. Without that layer, an agent-authored delta to an SCR-relevant spec merges with no governance, breaching Article 121.
- **DORA Articles 6, 8, and 11 (ICT risk management framework, identification and protection of critical functions, response and recovery):** OpenSpec writes specs and merges deltas with no runtime classification of whether the affected component is an ICT critical function. Allianz must operate a DORA-classification layer outside OpenSpec that gates `/opsx:archive` on critical-function specs, blocks merges without an attached recovery plan, and routes critical-function changes through DORA Article 28 (third-party risk) review when the agent is an external LLM. Convention-level separation does not meet DORA Article 6's requirement that the ICT risk management framework be `documented and approved` and operationally enforced.
- **EU AI Act Article 9 (risk management system), Article 15 (accuracy, robustness, cybersecurity), and Annex III §5 (insurance-pricing high-risk systems):** for any pricing, underwriting, or claims model classified as high-risk under Annex III, OpenSpec's lack of runtime enforcement, lack of evaluation gates, and lack of observability hooks means the framework alone cannot evidence Article 9 risk-management completeness or Article 15 robustness. Allianz must augment with an independent runtime policy envelope, evaluation harness, and trace pipeline before deploying any OpenSpec-driven change to a high-risk system.
- **SR 11-7 §IV.A and §V (model implementation, use, validation, governance):** OpenSpec's delta-merge model satisfies §III.B (model documentation) at the artefact level but provides no §V model risk management framework — no inventory, no tiering by materiality, no validation independence enforcement. Allianz must operate a model-risk-management layer outside OpenSpec that classifies each spec by §V tier, attaches the validator's organisational independence record, and prevents archive of material-model deltas without independent validation sign-off.
- **GDPR Article 22 (automated individual decision-making) and Article 25 (data protection by design and by default):** specifications that touch personal data processing or automated insurance decisions need data-protection-impact-assessment linkage and processing-purpose enforcement at the artefact level. OpenSpec offers no schema field for DPIA reference, lawful-basis tagging, or special-category-data classification. Allianz must extend `OpenSpec/openspec/schemas/` with a custom Article 25-aligned schema and refuse to archive deltas that mutate personal-data processing without DPIA evidence; OpenSpec does not enforce this by default.
