# P4 — Right-size the swarm | **38/100**

## What OpenSpec asserts about this principle

OpenSpec is a single-thread, single-agent spec scaffolding workflow — not a swarm coordination framework. `OpenSpec/README.md` describes the operating loop as `/opsx:propose ──► /opsx:apply ──► /opsx:sync ──► /opsx:archive`, executed by one assistant ("tell your AI"). `OpenSpec/docs/concepts.md` claims artefacts form a dependency graph (`proposal → specs → design → tasks → implement`) where "Dependencies are enablers, not gates" and where "Human + Agent Collaboration" is intended as a one-human / one-agent loop: "Human provides intent, context, and constraints. Agent converts this into behavior-first requirements and scenarios." `OpenSpec/docs/workflows.md` admits parallelism only at the change-folder level: "Multiple changes can exist simultaneously without conflicting", with `/opsx:bulk-archive` as the post-hoc reconciliation surface. The only explicit conflict-resolution machinery for parallel work is described in `OpenSpec/openspec-parallel-merge-plan.md`, which acknowledges: "The tooling cannot detect divergence between the change author's starting point and the live spec, so parallel development corrupts the source of truth without warning." OpenSpec asserts no concept of agent specialisation, structured disagreement, adversarial review, tier containment for sub-agents, or typed-versioned shared state for swarm coordination.

## What works

- Single-commit-path enforcement at the spec level is the explicit design intent. `OpenSpec/docs/concepts.md` states "Specs are the source of truth" and the archive process is described as "Each delta spec section (ADDED/MODIFIED/REMOVED) is applied to the corresponding main spec" — there is exactly one merge surface, which aligns with the manifesto's "swarms propose; a single commit path commits" instruction.
- Default-to-simplest-topology behaviour is structurally enforced. `OpenSpec/README.md` lists the `core` profile as default with five commands (`/opsx:propose`, `/opsx:explore`, `/opsx:apply`, `/opsx:sync`, `/opsx:archive`) and the expanded profile is opt-in via `openspec config profile`. Users do not graduate to coordination complexity by default.
- Parallelism is bounded to the change-folder unit. `OpenSpec/docs/workflows.md` ("Parallel Changes" section) constrains concurrent work to change folders that do not touch the same delta spec, which produces a defined commutativity property at the file-system level rather than at agent level.
- Conflict detection at archive time is explicitly recognised as a gap and roadmapped in `OpenSpec/openspec-parallel-merge-plan.md` Phase 0 ("Persist requirement fingerprints alongside each change" and "Validate fingerprints during archive") — the failure mode (silent scenario drop when Change A then Change B archive sequentially) is named and a hash-based detection mechanism is specified, even if not yet shipped.
- Schema-driven artefact dependencies in `OpenSpec/openspec/specs/` (e.g. `schema-validate-command/spec.md`, `schema-init-command/spec.md`) impose a deterministic ordering (`proposal → specs → design → tasks`) that prevents one ad-hoc agent from racing past artefact prerequisites — this acts as a cheap topology constraint where it exists.
- Verification is offered as a separate command in the expanded profile. `OpenSpec/docs/workflows.md` describes `/opsx:verify` checking "COMPLETENESS / CORRECTNESS / COHERENCE" as a distinct invocation, not as a parallel adversarial reviewer agent, but as a structurally separable role that an organisation is free to assign to a different operator.

## Where it fails the manifesto's bar

- Manifesto P4 requires: "If shared state is not typed, versioned, and reconciled, the swarm is a mob." OpenSpec's shared state — `openspec/specs/` and `openspec/changes/` — is markdown plus untyped folder conventions. `OpenSpec/openspec-parallel-merge-plan.md` admits: "The delta format (`src/core/parsers/requirement-blocks.ts:113`) has no notion of base versions or scenario-level operations" and "Changes do not persist the requirement content they were authored against, so the archive step cannot tell if the live spec diverged." There is no typed schema enforced at runtime, no version vector, and no reconciliation primitive — failing the minimum bar directly. For Allianz this falls under DORA Art. 9 (ICT risk integrity controls) and SR 11-7 §IV.A (model documentation completeness): silent loss of approved requirements is a model-governance integrity failure.
- Manifesto P4 requires: "An orchestrator cannot delegate actions to specialist agents that exceed its own authorized autonomy tier. Tier elevation requires the same approval path regardless of whether the request originates from a human or an orchestrating agent." OpenSpec has no orchestrator concept, no tier model, and no propagation of authority across delegated calls. `OpenSpec/AGENTS.md` is empty (1 line). `OpenSpec/docs/concepts.md` defines no agent-to-agent delegation surface. This is a scope gap with regulatory exposure under EU AI Act Art. 14 (human oversight): if Allianz wires OpenSpec into a multi-agent stack, OpenSpec contributes zero containment for tier escalation.
- Manifesto P4 requires: "Design conflict resolution, not just parallelism." `OpenSpec/openspec-parallel-merge-plan.md` documents the inverse — "The CLI never forces contributors to reconcile parallel updates. There is no equivalent of `git merge`, `git rebase`, or conflict markers" — and `/opsx:bulk-archive` in `OpenSpec/docs/workflows.md` performs detection only ("Inspecting codebase to resolve... Both changes are implemented. Will apply in chronological order") with no structured-disagreement protocol. Under Solvency II Art. 121 (model change governance), Allianz cannot rely on "chronological order" to reconcile competing model documentation deltas.
- Manifesto P4 requires: "The point of a swarm is not to mimic an organization chart. It is to create structured disagreement, specialization, and reconciliation where the workload benefits from multiple perspectives." OpenSpec's role surface in `OpenSpec/docs/concepts.md` ("Human + Agent Collaboration") instantiates exactly one role pair — human intent, agent drafter — with no adversarial specialisation (no separate spec-critic, no independent threat modeller, no release-risk assessor). Under SR 11-7 §V.B (effective challenge), one drafter without an organisationally separate critic is non-compliant model risk practice.
- Manifesto P4 requires: "a swarm that only writes code while governance remains a separate human overlay is not a governed agentic system." OpenSpec restricts its agent loop to artefact drafting and code application (`/opsx:apply` in `OpenSpec/docs/workflows.md`); governance work — specification critique, threat modelling, evidence assembly, release risk assessment — is left to the human operator and is not a first-class agent role. EU AI Act Art. 9 (risk management system) requires governance work to be performed and logged; OpenSpec offers no agent surface to instrument it.
- Manifesto P4 requires (signal for scaling beyond a single agent): "The task requires adversarial specialization — roles whose objectives conflict and cannot be fully trusted from the same agent (e.g., implementation and independent security review)." OpenSpec collapses both roles into the same `/opsx:apply` execution. `OpenSpec/docs/workflows.md` describes verify as `/opsx:verify` invoked by the same operator/agent, with no organisational separation requirement. For Allianz under DORA Art. 6 (governance and control framework), independent challenge is mandatory; OpenSpec does not scaffold it.
- Manifesto P4 requires: "Choose the simplest topology that solves the problem and graduate to more complex coordination only when evidence shows it is needed." OpenSpec defaults correctly to single-agent, but provides no measurement substrate (no evaluation pass-rate telemetry, no context-saturation metric, no concurrency contention counter) to detect when a single agent is insufficient. The evidence-driven graduation criterion in P4 is therefore unactionable inside OpenSpec.
- Manifesto P4 requires versioned, reconciled shared state. `OpenSpec/openspec-parallel-merge-plan.md` Phase 3 ("Define stable requirement IDs", "Model spec edits as operations over an AST", "operational transforms or CRDT-like techniques") names the necessary mechanisms as long-term roadmap items, not current capability. Marking these as `_[Planned, not operational]_` and assigning zero score weight: the current state is replace-based markdown substitution. Under Solvency II Art. 124 (documentation), this is insufficient to evidence model change history.

## Allianz-specific implications

- **Solvency II Art. 121–124 (model change governance and documentation):** OpenSpec's silent-overwrite failure mode in `OpenSpec/openspec-parallel-merge-plan.md` is incompatible with internal-model documentation integrity for Allianz Solvency II SCR models. Allianz MUST gate OpenSpec adoption for any Solvency II model-scope artefact behind the Phase 0 fingerprint guard or refuse to use OpenSpec for that scope until fingerprinting ships and is verified.
- **DORA Art. 9 (ICT risk — integrity) and Art. 6 (governance):** parallel-archive scenario loss is an ICT integrity incident class. Allianz MUST add an external git-tag-and-hash attestation around `openspec archive` events for any artefact in DORA ICT scope and MUST log every `/opsx:bulk-archive` chronological-order resolution as a manual integrity decision in the ICT risk register (`operational-templates/ai-risk-register.md`).
- **EU AI Act Art. 14 (human oversight) and Annex III §5(b) (insurance high-risk use):** OpenSpec offers no agent-tier containment, so where Allianz wires OpenSpec into pricing, underwriting, or claims agent stacks for personal lines, OpenSpec MUST be operated at AEM Tier 1 (observe only) per the hard autonomy caps in `domains/insurance.md` ("Underwriting decisions for individual cover (personal lines) — Tier 1 (observe only)"). Allianz MUST forbid `/opsx:apply` from emitting code that touches a high-risk Annex III decision pathway without an independent human merge.
- **SR 11-7 §V.B (effective challenge) and §IV.A (model documentation):** OpenSpec's single-drafter loop does not produce effective challenge. Allianz MUST require a second, organisationally separate operator (or a distinct evaluator agent run by a different team) to invoke `/opsx:verify` on every change folder before `/opsx:archive`, and MUST record that operator's identity in `meta.json` for every Solvency II or SR 11-7 in-scope spec change.
- **GDPR Art. 22 and Art. 25 (data protection by design):** OpenSpec lacks adversarial-specialisation roles such as a privacy reviewer. For Allianz processing of special-category health data (claims, life and health underwriting), the framework's drafter/applier loop is insufficient. Allianz MUST embed a separate DPO-aligned review step outside OpenSpec for any `proposal.md` or `design.md` that touches GDPR Art. 9 special categories, since OpenSpec provides no agent role to instantiate that review.

## Score rationale

Score: **38/100** (Critical). Evidence-for: OpenSpec defaults to a single-agent loop, which is the manifesto's preferred topology when no signal demands more (`OpenSpec/README.md`, `OpenSpec/docs/workflows.md`); maintains a single commit path through the archive merge surface (`OpenSpec/docs/concepts.md`); bounds parallelism to change folders; and explicitly recognises the parallel-merge corruption failure in `OpenSpec/openspec-parallel-merge-plan.md`, naming hash-based fingerprinting and 3-way merge as the remediation. Evidence-against: the manifesto P4 minimum bar "If shared state is not typed, versioned, and reconciled, the swarm is a mob" is failed at runtime — OpenSpec shared state is untyped markdown without base-version fingerprints, and `OpenSpec/openspec-parallel-merge-plan.md` admits the archive step cannot detect divergence; the tier-containment minimum bar is structurally absent (no orchestrator, no tier model, no delegated-authority propagation); structured-disagreement specialisation (spec critique, threat modelling, release-risk assessment) is not instantiated as agent roles; conflict resolution is post-hoc chronological rather than designed; the evidence-driven graduation criterion is unactionable because no telemetry substrate exists. The "what works" set credits real but mostly negative-space behaviour (defaulting to simplicity, single commit path); the "where it fails" set documents direct minimum-bar failures with regulatory exposure under DORA Art. 9, Solvency II Art. 121–124, SR 11-7 §IV.A and §V.B, EU AI Act Art. 14 and Annex III, and GDPR Art. 9 and 22. The score sits in the upper Critical band because the single-agent default is correct by P4 standards even though the supporting machinery for safe scaling is absent.
