# P6 — Knowledge and memory are infrastructure | **38/100**

> Manifesto: arnaudgelas/agentic-engineering-manifesto@08123c263794b5cc24dbb3e1a5897a74288026e9
> Review date: 2026-05-08. Framework: OpenSpec 1.3.1. Organisation: Allianz. Industry: European insurance — SR 11-7, DORA, EU AI Act, GDPR, Solvency II.

## What OpenSpec asserts about this principle

OpenSpec asserts that the `openspec/specs/` tree is the project's "source of truth" for current behaviour, and that all evolution flows through delta artefacts that are reconciled into it. `docs/concepts.md` "Glossary" states: "**Source of truth** — The `openspec/specs/` directory, containing the current agreed-upon behavior". `openspec/specs/cli-archive/spec.md` Requirement: "Spec Updates Before Archiving" states "Before moving the change to archive, the command SHALL apply delta changes to main specs to reflect the deployed reality" and `openspec/specs/specs-sync-skill/spec.md` defines the `/opsx:sync` reconciliation logic for `## ADDED Requirements`, `## MODIFIED Requirements`, `## REMOVED Requirements`, and `## RENAMED Requirements`. `docs/concepts.md` "Why Archive Matters" claims the archive provides "Audit trail. The archive preserves the full context of every change — not just what changed, but the proposal explaining why, the design explaining how, and the tasks showing the work done." OpenSpec asserts nothing about *learned memory*: no source file in `OpenSpec/openspec/specs/` defines memory provenance, expiry, decay, rollback, domain scoping, agent-authorship labelling, or skill-artefact governance.

## What works

- `openspec/specs/cli-archive/spec.md` Requirement: "Spec Updates Before Archiving" enforces that delta artefacts are applied to `openspec/specs/` before archival, giving knowledge a single, governed write path with clear ADDED/MODIFIED/REMOVED/RENAMED operations enumerated in `openspec/specs/specs-sync-skill/spec.md` Requirement: "Delta Reconciliation Logic".
- `openspec/specs/cli-validate/spec.md` Requirement: "Bulk and filtered validation" provides `openspec validate --all --strict --json` which fails CI on malformed knowledge artefacts, preventing schema drift in the knowledge store before archive merges deltas.
- `docs/concepts.md` "Delta Sections" formalises that knowledge mutates only through typed delta operations (`## ADDED Requirements` "Appended to main spec", `## MODIFIED Requirements` "Replaces existing requirement", `## REMOVED Requirements` "Deleted from main spec"), so every change to ground-truth specs leaves a typed, reviewable trail in the change folder.
- `docs/concepts.md` "Archive Process" preserves the originating proposal, design, tasks, and deltas in `changes/archive/` with a date prefix, retaining the historical knowledge state alongside the current `openspec/specs/` snapshot — point-in-time reconstruction of *knowledge* (not memory) is therefore possible from `git log` plus the archive folder.
- `openspec/specs/specs-sync-skill/spec.md` Requirement: "Specs Sync Skill" Scenario "Idempotent operation" guarantees repeated syncs produce identical results, eliminating one class of consistency-under-concurrency failure for the knowledge store.
- `openspec/specs/context-injection/spec.md` Requirement: "Inject context into all artifact instructions" and `openspec/specs/rules-injection/spec.md` Requirement: "Inject rules only for matching artifact" allow project-level context (tech stack, conventions) and per-artefact rules to be versioned in `openspec/config.yaml` and injected deterministically into agent instructions, treating prompt-context as versioned configuration rather than ad-hoc memory.

## Where it fails the manifesto's bar

- "**Learned memory** is heuristic: reasoning patterns, incident learnings, routing preferences, and reusable skills. It is probabilistic, subject to decay, and requires continuous renewal" (`manifesto-principles.md` §6). OpenSpec has no learned-memory construct at all. No file under `OpenSpec/openspec/specs/` defines a memory store, decay schedule, or renewal mechanism; `/opsx:verify`, `/opsx:sync`, and `/opsx:archive` operate purely on Markdown knowledge artefacts. Convention-not-enforcement / scope-gap. Under EU AI Act Art. 9 (risk management system) Allianz cannot demonstrate continuous-renewal evidence for any agent that learns from claims-history feedback loops.
- "if it changes through governed processes (pull requests, ADR reviews, schema migrations), it is knowledge. If it changes through feedback loops (agent learning, incident adaptation, routing optimization), it is learned memory. The governance mechanism determines the classification" (`manifesto-principles.md` §6). OpenSpec's `openspec/specs/cli-archive/spec.md` Requirement: "Archive Process" governs only the knowledge path; no artefact in OpenSpec source distinguishes feedback-loop-driven mutations from PR-driven ones. Absent. This conflates the two classes for Solvency II Art. 121 (statistical quality standards) where model-feedback updates require a different evidence trail from spec changes.
- "If memory cannot expire, be rolled back, or show provenance, it is not memory — it is a liability" (`manifesto-principles.md` §6 minimum bar). OpenSpec provides no expiry, no rollback, and no provenance mechanism for any agent state beyond Markdown specs. `openspec/specs/cli-archive/spec.md` does not define an `unarchive` or revert operation; `docs/workflows.md` line 375 mentions "Simpler rollback if needed" only as a narrative aside, not as a specified mechanism. Absent. Under DORA Art. 12 (backup, restoration, recovery) Allianz cannot evidence rollback for any agent memory state.
- "Provenance, expiration, compression, rollback, and domain scoping are the mechanisms of that renewal cycle" (`manifesto-principles.md` §6). None of these five mechanisms appears as a Requirement in `OpenSpec/openspec/specs/`. Domain scoping is hinted at in `docs/concepts.md` Glossary entry "Domain — A logical grouping for specs (e.g., `auth/`, `payments/`)" but is a *spec organisation* convention, not a memory access-control boundary. Absent. EU AI Act Art. 10 (data and data governance) requires documented data lineage for high-risk AI training and operation — not satisfied.
- "if memory is not revalidated against current architecture and process before reuse, it is not being governed — it is being trusted" (`manifesto-principles.md` §6 minimum bar). `openspec/specs/opsx-verify-skill/spec.md` Requirement: "Coherence Verification" verifies coherence of *new* artefacts within a single change but does not revalidate previously archived knowledge or any agent memory before reuse. `openspec/specs/instruction-loader/spec.md` Requirement: "Template Enrichment" injects archived templates without a freshness check. Convention-not-enforcement. Under SR 11-7 §V.B (ongoing monitoring) Allianz must revalidate model assumptions before each material reuse — OpenSpec does not enforce this for any state agents carry forward.
- "**Knowledge contamination** — agent-generated content enters the knowledge base through governed processes (commits, ADRs, documentation PRs) and is subsequently retrieved in future context with the same epistemic authority as human-authored knowledge … Mitigate by requiring provenance labeling of all agent-authored artefacts at commit time" (`manifesto-principles.md` §6). OpenSpec mandates no agent-authorship label on archived specs. `openspec/specs/openspec-conventions/spec.md` references "authors" generically; nothing in `openspec/specs/cli-archive/spec.md` requires that an agent-authored requirement carry an `agent_authored: true` marker, model identifier, or system-instruction hash that travels with the artefact through retrieval. Absent. Under EU AI Act Art. 13 (transparency) and GDPR Art. 22 (automated decision-making), Allianz cannot distinguish agent-authored underwriting rules from human-authored ones once both live in `openspec/specs/`.
- "**Memory poisoning** — an agent writes incorrect learnings that corrupt future agent behavior across sessions. Mitigate with human review gates on memory writes from agents operating at Tier 2 or above" (`manifesto-principles.md` §6). OpenSpec provides no memory-write gate: there is no memory store and no Tier 2-above review requirement. `openspec/specs/cli-archive/spec.md` Requirement: "Archive Validation" Scenario "Force archive without validation" explicitly permits `openspec archive change-name --no-validate`, and `openspec/specs/opsx-verify-skill/spec.md` is non-blocking ("Does not block archive", `docs/commands.md` line 336). Convention-not-enforcement. Under DORA Art. 9 (protection and prevention) Allianz cannot demonstrate poisoning-resistance for agent state.
- "**Audit trail gap** — 'what version of memory was active when this decision was made?' requires point-in-time snapshots, not just current state, for meaningful incident reconstruction" (`manifesto-principles.md` §6). OpenSpec captures point-in-time *spec* state via `changes/archive/<date-prefix>` (`docs/concepts.md` "The Archive Process" item 2), but no artefact captures the agent's memory, retrieval-corpus version, or embedding-model version active at the moment of an agent decision. Partial — knowledge is snapshotted; memory is not. Under DORA Art. 17 (ICT-related incident management) Allianz cannot reconstruct the agent state active at incident time.
- "Agents can externalize procedures as reusable skill artifacts that evolve through experience without changing model weights. Those learned skills require the same provenance, review, rollback, and scoping discipline as any other memory layer" (`manifesto-principles.md` §6). OpenSpec ships agent *skills* (`openspec/specs/opsx-verify-skill/spec.md`, `openspec/specs/opsx-archive-skill/spec.md`, `openspec/specs/specs-sync-skill/spec.md`, `openspec/specs/opsx-onboard-skill/spec.md`) as static, repository-versioned Markdown — none of these defines a runtime evolution path, provenance record, scoping boundary, or rollback for skills that learn from experience. Scope gap with flag: the framework does not target experience-evolving skill artefacts. Under ISO/IEC 42001 clause A.3.2 (AI roles and responsibilities) Allianz must assign accountability for skill evolution — OpenSpec gives it no anchor.

## Allianz-specific implications

- Solvency II Art. 121 (statistical quality standards) and Art. 124 (validation standards) require documented data lineage, model assumption tracking, and revalidation before material reuse for internal models. OpenSpec snapshots `openspec/specs/` knowledge state via `changes/archive/` (`docs/concepts.md` "The Archive Process") but captures no memory-state version, retrieval-corpus version, or embedding-model version. Allianz MUST extend `openspec/specs/cli-archive/spec.md` (or add a sibling spec) to require that archived changes capture an `agentic_provenance` block — foundation model identifier, system-instruction hash, retrieval-corpus version, embedding-model version — for every change touching an internal-model-scope agent, otherwise IMAP submissions for agent-assisted internal models will fail Solvency II Art. 112 documentation review.
- EU AI Act Art. 10 (data and data governance) and Art. 12 (record-keeping) mandate documented data lineage and automatic logging across the lifecycle for high-risk AI systems. OpenSpec has no provenance label distinguishing agent-authored from human-authored requirements once a delta is reconciled by `/opsx:sync` (`openspec/specs/specs-sync-skill/spec.md`). Allianz MUST add a mandatory `agent_authored: true | false` plus `model_identifier` field to every `### Requirement:` block produced through `/opsx:propose` for any agent in EU AI Act Annex III §5 scope (insurance pricing/underwriting), and enforce it via `openspec/specs/cli-validate/spec.md` strict mode, otherwise the Art. 10/12 evidence trail is incomplete.
- DORA Art. 12 (backup policies and procedures, restoration and recovery) requires demonstrable rollback for ICT-supporting components. OpenSpec has no `openspec unarchive` or revert command; `docs/workflows.md` line 375 mentions rollback only narratively. Allianz MUST specify and implement an inverse-archive operation that restores `openspec/specs/` to a prior `changes/archive/<date-prefix>` state and that captures the operator and reason in the archive itself, otherwise Allianz cannot evidence DORA Art. 12 recovery for the agent-governance toolchain.
- GDPR Art. 9 (special category data — health, genetic) and Art. 22 (automated individual decision-making) require demonstrable safeguards on automated processing, including the ability to explain which rules drove a decision (`domains/insurance.md` "GDPR and Special Category Data"). OpenSpec scenarios are prose; once an agent-drafted requirement is archived into `openspec/specs/` it is retrieved with the same epistemic authority as a human-authored requirement (`manifesto-principles.md` §6 "Knowledge contamination"). Allianz MUST refuse `openspec archive` for any change touching health- or genetic-data processing flows unless every agent-authored requirement carries a provenance label and a human reviewer's structured sign-off captured in the archived change folder.
- ISO/IEC 42001 clause A.3.2 (AI roles and responsibilities) and SR 11-7 §III.A (model risk management framework) require named accountability for model components and for memory-state changes. OpenSpec assigns accountability to neither learned memory (which it does not represent) nor skill artefacts (which it represents only as static Markdown in `openspec/specs/opsx-*-skill/spec.md`). Allianz MUST add a complementary `memory-governance/` spec set that names the four authorities (write, read, expire, rollback) per agent and that is enforced as a precondition to operating any agent above Tier 1 — OpenSpec alone cannot satisfy SR 11-7's model-component-ownership obligation for learned-memory-bearing agents.
