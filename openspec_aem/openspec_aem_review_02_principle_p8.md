# P8 — Evaluations are the contract | **34/100**

> Review date: 2026-05-08. Manifesto commit: `08123c263794b5cc24dbb3e1a5897a74288026e9`. Framework: OpenSpec 1.3.1. Organisation: Allianz. Industry: European insurance — DORA, Solvency II, EU AI Act, GDPR.

## What OpenSpec asserts about this principle

OpenSpec asserts that specifications are "behavior contracts" expressed as `### Requirement:` blocks containing `#### Scenario:` blocks in Given/When/Then form, and that the `/opsx:verify` skill (`openspec/specs/opsx-verify-skill/spec.md`) checks "Completeness, Correctness, and Coherence" of an implementation against the change's artefacts. The framework states that "scenarios are the 'when' — they provide concrete examples that can be verified" (`docs/concepts.md`) and provides `openspec validate` (`openspec/specs/cli-validate/spec.md`) which performs *structural* schema validation of spec/change Markdown — not behavioural evaluation. The verify skill explicitly notes "Scenario coverage check" produces a warning such as "Scenario 'System preference detection' has no test coverage" (`docs/commands.md` lines 350–376), confirming that authoring tests is left to the implementer and that warnings "don't block archive".

## Seven-Condition DoD Test (Evaluation Edition)

1. **Evaluations versioned and coupled to specifications.** *Partially met.* `#### Scenario:` blocks live alongside `### Requirement:` blocks in `openspec/specs/<id>/spec.md` and delta scenarios travel inside the change folder per `docs/concepts.md` "Delta Specs" section, so scenario text is versioned with the spec. However scenarios are prose, not executable evaluations; nothing in `openspec/specs/cli-validate/spec.md` or `openspec/specs/opsx-verify-skill/spec.md` binds a scenario to an automated test asset, fixture, or CI assertion.
2. **Coverage of happy path, adversarial cases, and regression scenarios.** *Absent.* The framework's only coverage construct is the prose "Scenario coverage check" in `openspec/specs/opsx-verify-skill/spec.md` (Requirement: Correctness Verification, Scenario: Scenario coverage check). No source file in `OpenSpec/openspec/specs/` requires adversarial categories, regression suites, or red-team scenarios; `docs/concepts.md` advises "Cover both happy path and edge cases" as guidance only.
3. **Evaluations evolve with the system — spec changes trigger evaluation changes.** *Partially met.* `openspec/specs/cli-archive/spec.md` and the delta-archive flow in `docs/concepts.md` ("Why Archive Matters") merge `## ADDED Requirements`, `## MODIFIED Requirements`, and `## REMOVED Requirements` into the source-of-truth spec, so scenario text follows the spec. There is no mechanism that re-runs or re-validates *executable* evaluations on spec change because no executable evaluation registry exists.
4. **Governance evaluations — evidence bundle completeness, provenance consistency, rollback procedure currency, SBOM completeness.** *Absent.* `openspec validate --all` (`openspec/specs/cli-validate/spec.md`, Requirement: Bulk and filtered validation) checks Markdown structure (`## Why`, `## What Changes`, scenario header form) and emits Zod schema errors with `{ level, path, message }`. It does not check evidence-bundle completeness, provenance consistency, rollback currency, or SBOM completeness. The `aem_components` schema in `governance/evidence-bundle-schema.md` has no counterpart artefact in OpenSpec.
5. **Verification (did we build it right?) separated from validation (did we build the right thing?).** *Absent.* `/opsx:verify` (`openspec/specs/opsx-verify-skill/spec.md`, Requirement: Coherence Verification) folds three concerns — completeness, correctness, coherence — into a single agent-run skill executed by the same author/agent that produced the implementation. The framework does not separate verification from validation, and `docs/concepts.md` does not name the distinction.
6. **Independent validation — organisationally separate, capable of blocking production deployment.** *Absent.* `/opsx:verify` produces "CRITICAL / WARNING / SUGGESTION" output that "Does not block archive, but surfaces issues" (`docs/commands.md` line 336). No artefact in `OpenSpec/openspec/specs/` defines an organisationally separate validator role, a blocking gate, or a sign-off authority.
7. **Governance evaluation failures trigger the same remediation sub-cycle as product failures.** *Absent.* OpenSpec has no governance evaluation suite, so this condition is structurally unreachable. `openspec/specs/cli-archive/spec.md` does not condition archival on any control-state evidence beyond Markdown shape.

## What works

- `openspec/specs/cli-validate/spec.md` defines machine-checkable structural validation (`openspec validate --all --strict --json`) that emits a stable JSON shape `{ items[], summary, version }` per the "JSON output schema for bulk validation" scenario, giving CI a non-zero exit on malformed specs.
- `openspec/specs/opsx-verify-skill/spec.md` Requirement: "Completeness Verification" mandates that the agent reads `tasks.md` and "counts tasks marked `- [x]` (complete) vs `- [ ]`" and "extracts all requirements from delta specs" then "searches codebase for implementation of each requirement", which is a lightweight requirement-to-code traceability check.
- `docs/concepts.md` "Spec Format" enforces the `### Requirement:` / `#### Scenario:` Given/When/Then structure with RFC 2119 keywords, and `openspec/specs/cli-validate/spec.md` Requirement "Validator SHALL detect likely misformatted scenarios and warn with a fix" prevents scenario drift from the canonical form.
- The delta model (`openspec/specs/change-creation/spec.md`, `docs/concepts.md` "Delta Specs") ties scenario edits to `## ADDED Requirements` / `## MODIFIED Requirements` / `## REMOVED Requirements` blocks, so scenario evolution is auditable in change folders before archive merges them into `openspec/specs/`.
- `openspec/specs/cli-validate/spec.md` Requirement "Invalid results SHALL include a Next steps footer" gives reviewers actionable remediation guidance, reducing rubber-stamping at the structural layer.
- `openspec/specs/opsx-verify-skill/spec.md` Requirement: "Verification Report Format" prescribes a CRITICAL/WARNING/SUGGESTION priority scheme with "specific, actionable fix recommendation" and explicitly bans vague language in review output, providing a small empirical anchor for review-output quality.

## Where it fails the manifesto's bar

- "Evaluations define what 'correct' means in terms the system can check autonomously" (`manifesto-principles.md` §8). OpenSpec scenarios are Markdown prose interpreted by an agent, not executable evaluations. `openspec/specs/cli-validate/spec.md` validates Markdown shape; no command runs scenario assertions against a build. This is convention-not-enforcement and exposes Allianz to DORA Art. 6(2) ICT-risk-management failures because the change-management trail contains no machine-verified correctness evidence.
- "If evaluations do not include regression cases, verification is incomplete" (`manifesto-principles.md` §8 minimum bar). No file under `OpenSpec/openspec/specs/` requires regression scenarios, regression suites, or a regression catalogue; the only coverage construct is `openspec/specs/opsx-verify-skill/spec.md` "Scenario coverage check" which warns and does not block. Solvency II Art. 124 (validation standards) requires statistical backtesting and stability testing — OpenSpec records neither.
- "Passing evaluations satisfies verification. It does not satisfy validation or independent validation" (`manifesto-principles.md` §8). `/opsx:verify` (`openspec/specs/opsx-verify-skill/spec.md`) collapses verification, validation, and coherence into one agent-run check executed by the same actor who produced the implementation. EU AI Act Art. 17 (quality management system for high-risk AI) requires distinct verification and validation procedures; OpenSpec does not provide them.
- "Independent validation must be capable of blocking production deployment. A team that can only observe and advise is not independent validation — it is a consultation" (`manifesto-principles.md` §8). `/opsx:verify` "Does not block archive" (`docs/commands.md` line 336) and `openspec/specs/cli-archive/spec.md` archives a change once tasks are checked. This is advisory-only against Solvency II Art. 48 (actuarial function) and SR 11-7 §V (effective challenge), which require a blocking, organisationally separate validator.
- "Evaluations must also test whether the governance system works — not only whether the product works" (`manifesto-principles.md` §8). OpenSpec has no governance evaluation suite. `governance/evidence-bundle-schema.md` `aem_components` (evidence bundle completeness, provenance consistency, control state record accuracy, rollback procedure currency, SBOM completeness) has no matching command, schema, or check in OpenSpec source files. DORA Art. 16 (digital operational resilience testing) and EU AI Act Art. 9 (risk management system) both require governance-level evaluation evidence.
- "Every change must be verified against the evaluation suite — and every change must preserve or improve evaluation performance" (`manifesto-principles.md` §8). `openspec/specs/cli-archive/spec.md` does not condition archival on any evaluation pass-rate metric, regression delta, or coverage non-decrease. Archive proceeds on Markdown well-formedness alone, which fails the EU AI Act Art. 15 (accuracy, robustness, cybersecurity) substance test for high-risk AI systems.
- "Evaluations are the machine-readable form of the acceptance criteria in Principle 2" (`manifesto-principles.md` §8). Scenarios in `openspec/specs/<id>/spec.md` are not machine-readable acceptance criteria — they are natural-language prose. `openspec/specs/cli-validate/spec.md` parses headings and bullet shape; it does not parse `WHEN`/`THEN` semantics. Solvency II Art. 121 (statistical quality standards) requires testable acceptance criteria, which OpenSpec scenarios do not constitute.
- "When governance evaluations fail, they trigger the same remediation sub-cycle as product evaluation failures — not a separate audit process" (`manifesto-principles.md` §8). OpenSpec has neither a governance evaluation construct nor a remediation sub-cycle linkage. `openspec/specs/cli-validate/spec.md` "Next steps footer" is a textual hint, not a control. Under DORA Art. 17 (ICT-related incident management) Allianz cannot demonstrate that governance failures and product failures share a remediation pipeline.

## Allianz-specific implications

- Solvency II Art. 121 (statistical quality standards) and Art. 124 (validation standards) require validation independent of model development with documented backtesting against historical claims and pricing data. OpenSpec's `/opsx:verify` (`openspec/specs/opsx-verify-skill/spec.md`) is run by the same agent as the implementer and is non-blocking; Allianz MUST add an organisationally separate validator role with a blocking gate enforced outside the OpenSpec archive flow before any internal-model agent change proceeds to production.
- EU AI Act Art. 9 (risk management) and Art. 15 (accuracy, robustness, cybersecurity) require continuous evaluation across the lifecycle for high-risk AI systems. OpenSpec scenarios are not executable and no regression catalogue is enforced; Allianz MUST bind every `#### Scenario:` to an executable test artefact in CI and refuse archive when regression coverage decreases, because non-decrease is not enforced by `openspec/specs/cli-archive/spec.md`.
- DORA Art. 24–26 (Threat-Led Penetration Testing) and Art. 16 (digital operational resilience testing) require adversarial testing of critical ICT systems. OpenSpec contains no adversarial scenario category or red-team artefact in `OpenSpec/openspec/specs/`; Allianz MUST add a mandatory `## Adversarial Scenarios` section to delta specs for any agent system in DORA scope and wire it to a TLPT-equivalent harness that blocks `openspec archive`.
- GDPR Art. 22 (automated individual decision-making) and Art. 35 (DPIA) require demonstrable safeguards including fairness testing for special-category-data-driven decisions (insurance health/genetic data, `domains/insurance.md` "GDPR and Special Category Data"). OpenSpec scenarios do not encode fairness assertions; Allianz MUST extend the scenario catalogue to include fairness categories with disparity-metric thresholds and refuse `openspec archive` when thresholds are breached.
- SR 11-7 §V (effective challenge) and Solvency II Art. 48 (actuarial function) both require qualified, independent challenge with blocking authority. The advisory-only `/opsx:verify` design (`docs/commands.md` line 336: "Does not block archive") fails both. Allianz MUST insert a second-line actuarial validation gate that consumes OpenSpec's structured JSON output (`openspec/specs/cli-validate/spec.md` "JSON output schema for bulk validation") and is the sole authority over deployment for Solvency II internal-model agents.

## Score rationale

Score: **34/100** (Major gaps). Evidence-for: OpenSpec ships a structural validator (`openspec/specs/cli-validate/spec.md`) with strict-mode JSON output that is CI-consumable; the `### Requirement:` / `#### Scenario:` Given/When/Then format with RFC 2119 keywords (`docs/concepts.md` "Spec Format") provides a disciplined acceptance-criterion shape; the delta model in `openspec/specs/change-creation/spec.md` versions scenario evolution alongside specs; and `/opsx:verify` (`openspec/specs/opsx-verify-skill/spec.md`) defines a three-dimension review (completeness, correctness, coherence) with a CRITICAL/WARNING/SUGGESTION report and an explicit ban on vague language. Evidence-against: scenarios are prose, not executable evaluations; no command in `OpenSpec/openspec/specs/` binds a scenario to an automated test, regression catalogue, or adversarial harness; coverage is advisory ("Does not block archive", `docs/commands.md` line 336); verification, validation, and independent validation are collapsed into one agent-run skill rather than separated as `manifesto-principles.md` §8 requires; governance evaluations (evidence-bundle completeness, provenance consistency, rollback currency, SBOM completeness per `governance/evidence-bundle-schema.md` `aem_components`) have no counterpart artefact; archive does not gate on regression non-decrease or evaluation pass rate; and there is no organisationally separate, blocking validator. The aggregate result is a structural-only evaluation regime that fails the manifesto's contract test and fails Solvency II Art. 121/124, EU AI Act Art. 9/15/17, DORA Art. 16/24, and SR 11-7 §V for Allianz's regulated agent use cases.
