# P2 — Specifications are living artifacts | **72/100**

## What OpenSpec asserts about this principle

OpenSpec is positioned as a "spec framework" whose explicit purpose is to make specifications the artefact AI agents and humans agree on before code is written. `OpenSpec/docs/concepts.md` states: "Specs describe your system's behavior using structured requirements and scenarios" and "Specs are the source of truth — they describe how your system currently behaves." The framework separates source-of-truth specs (`openspec/specs/`) from in-flight modifications (`openspec/changes/<change>/specs/`) and represents every change as a delta with `## ADDED Requirements`, `## MODIFIED Requirements`, `## REMOVED Requirements`, and `## RENAMED Requirements` sections (`OpenSpec/schemas/spec-driven/schema.yaml`, `OpenSpec/docs/concepts.md` "Delta Specs"). The `openspec validate` command is documented in `OpenSpec/docs/cli.md` as a Validation surface that supports `--all --json` for bulk validation and is callable by agents. Specs use RFC 2119 keywords (`MUST`, `SHALL`, `SHOULD`, `MAY`) and Given/When/Then scenarios as normative content (`OpenSpec/docs/concepts.md` "Spec Format"). The framework's stated philosophy — `→ fluid not rigid`, `→ iterative not waterfall` — explicitly endorses the manifesto's "specifications are hypotheses that sharpen as agents explore" stance.

## What works

- **Specifications are first-class versioned artefacts under git.** Every spec lives at a deterministic path (`openspec/specs/<domain>/spec.md`) and every proposed change is a folder under `openspec/changes/<change>/` with `proposal.md`, `design.md`, `tasks.md`, and delta specs (`OpenSpec/docs/concepts.md` "Change Structure"). Both directories are intended to be checked into git, satisfying the manifesto's "versioned" requirement at the repository level.
- **Delta semantics are explicit and machine-parseable.** `OpenSpec/docs/concepts.md` documents `ADDED Requirements`, `MODIFIED Requirements`, `REMOVED Requirements`, and `RENAMED Requirements` as the only operations a change can express against existing specs, and `OpenSpec/schemas/spec-driven/schema.yaml` enforces this via the `specs` artefact instruction ("Use FROM:/TO: format" for renames; "MUST include full updated content" for modifications). This makes spec evolution diffable rather than narrative.
- **Validation is a CLI primitive callable by agents.** `OpenSpec/docs/cli.md` lists `openspec validate`, `openspec validate --all --json`, and `openspec status` as JSON-output commands "designed for agent/script use" — the spec is therefore not just documentation but is checkable in CI and by the agent itself.
- **Brownfield evolution is the default model, not an edge case.** `OpenSpec/docs/concepts.md` "Brownfield-first" and "Why Deltas Instead of Full Specs" frame iteration on existing specs as the primary use case; the archive process (`OpenSpec/docs/concepts.md` "The Archive Process") merges deltas into the source-of-truth spec and moves the change folder to `changes/archive/<YYYY-MM-DD>-<change>/`, preserving both the new spec state and the proposal/design/tasks that produced it.
- **The proposal/spec/design/tasks split keeps "what" separate from "how".** `OpenSpec/schemas/spec-driven/schema.yaml` separates `proposal` (why), `specs` (what), `design` (how), and `tasks` (steps). The schema instruction explicitly tells agents: "Avoid in specs: internal class/function names, library or framework choices, step-by-step implementation details" (`OpenSpec/docs/concepts.md` "What a Spec Is (and Is Not)"). This aligns with P2's "express what must be true when the work is complete".
- **Re-iteration is the documented loop.** `OpenSpec/docs/workflows.md` describes `/opsx:propose`, `/opsx:apply`, `/opsx:verify`, and `/opsx:archive` as a cycle in which the spec is updated when implementation reveals it was wrong; `OpenSpec/docs/concepts.md` "When to update the proposal/design" sections name "scope changes", "intent clarifies", and "implementation reveals the approach won't work" as legitimate triggers to mutate the artefact in-flight.
- **Schema dependencies are declared, not hardcoded.** `OpenSpec/docs/concepts.md` "Schemas" and `OpenSpec/docs/customization.md` describe `schema.yaml` files (e.g., `OpenSpec/schemas/spec-driven/schema.yaml`) where artefact dependencies are declared as data; teams can fork (`openspec schema fork`) and version their own workflow shape. This is closer to the manifesto's "machine-readable" bar than free-form markdown alone.

## Where it fails the manifesto's bar

- The manifesto requires that "Requirements, constraints, and acceptance criteria must be versioned, reviewable, and machine-readable — because they drive agent behavior directly" (`manifesto-principles.md` §2). OpenSpec stores specs as Markdown with conventional `### Requirement:` and `#### Scenario:` headings (`OpenSpec/docs/concepts.md` "Spec Format"), but provides no JSON Schema, no requirement IDs, no acceptance-criterion identifiers, and no machine-resolvable link from a requirement to the evaluations or tests that verify it. `openspec validate` checks structural conformance to the markdown convention; it does not check that a requirement is exercised by any executable evaluation. For Allianz, this means a Solvency II model documentation requirement and an EU AI Act Art. 9 risk-control requirement are both "free-text headings under a Markdown convention" with no traceable identifier.
- The manifesto requires that specifications be "reviewed, and revised based on execution evidence" and that "If a specification cannot be versioned, reviewed, and revised based on execution evidence, it is a wish, not an engineering artifact" (`manifesto-principles.md` §2 minimum bar). OpenSpec provides no formal review gate, no signed approval, no reviewer identity capture, and no required link from a spec change to execution evidence. `OpenSpec/docs/workflows.md` and `OpenSpec/docs/commands.md` describe `/opsx:verify` as an optional check that "implementation matches specs"; nothing forces a human reviewer to sign the spec before `/opsx:apply` runs. For Allianz under DORA Art. 6 (ICT risk management framework approval) and SR 11-7 §IV.A (effective challenge), absence of a captured reviewer identity is a control gap.
- The manifesto requires that "Specifications and architectural constraints operate at different layers and change at different speeds" and that "If the system cannot distinguish these two change types, specification iteration will silently erode architectural boundaries" (`manifesto-principles.md` §2; `companion/principles.md` "Specifications vs. Constraints"). OpenSpec does not distinguish a spec change from a constraint change. A delta in `openspec/changes/<change>/specs/auth/spec.md` that relaxes a `MUST` to a `SHOULD` is structurally indistinguishable from a delta that adds a new acceptance criterion; both archive through the same path with no governed-review trigger. For Allianz, this means a constraint relaxation touching GDPR Art. 25 (data protection by design) or EU AI Act Art. 15 (cybersecurity) would archive on the same gate as a UI scenario tweak.
- The manifesto requires four convergence stop conditions: "Acceptance criteria remain stable across three consecutive iterations", "Scope is contracting, not expanding", "Agent first-pass verification rate exceeds 80%", and "No new stop criteria emerge in the last iteration" (`manifesto-principles.md` §2). OpenSpec ships none of these as instrumented metrics. `openspec status` (`OpenSpec/docs/cli.md`) reports artefact progress, not iteration-stability, scope-direction, or first-pass rate. For Allianz, the absence of a measurable convergence signal means a Solvency II internal-model spec cannot evidence "specification is done iterating" except by reviewer attestation.
- The manifesto requires that the spec be "machine-readable — because they drive agent behavior directly" (`manifesto-principles.md` §2). OpenSpec's specs are Markdown with prose Given/When/Then under `#### Scenario:` headings (`OpenSpec/docs/concepts.md`); there is no formal grammar that a non-LLM consumer (a policy engine, a contract-test generator, a regulator's audit tool) can parse without re-interpreting natural language. The `--json` flag on `openspec list`, `show`, and `validate` (`OpenSpec/docs/cli.md`) returns JSON envelopes around the same Markdown body — it does not project requirements into a structured schema. For Allianz under EU AI Act Art. 11 (technical documentation) and Annex IV, this is a documentation-format gap, not a documentation-substance gap.
- The manifesto requires that specifications be "revised based on execution evidence" (`manifesto-principles.md` §2 minimum bar), and `manifesto-done.md` ties spec evolution to evaluation reports, trace IDs, diffs, and policy outputs as part of the seven-condition Definition of Done. OpenSpec's archive process (`OpenSpec/docs/concepts.md` "The Archive Process") merges deltas into specs based on "tasks complete" and an optional `/opsx:verify`; it does not require an evaluation report, a trace ID, or a policy-check output to be attached to the change before deltas are applied. For Allianz, this breaks the chain from a Solvency II Art. 121 model-change record back to the evidence that justified the change.

## Allianz-specific implications

- **Solvency II Art. 121 (validation standards) and Art. 124 (documentation standards).** OpenSpec's Markdown specs and `openspec/changes/archive/` produce a chronological record of what changed and why, but lack the structured model-documentation format that supervisory authorities require (`domains/insurance.md` "Documentation standards" row). Allianz MUST add a translation layer that exports each archived spec into the supervisory-prescribed format and binds the export to the archive commit hash, and MUST add a calibration section reviewable by the actuarial function before any spec touching SCR-relevant behaviour is archived.
- **DORA Art. 6 (ICT risk management framework) and Art. 9 (protection and prevention).** Spec changes touching ICT controls in Allianz's perimeter must be approved by the management body or a delegated function and recorded with reviewer identity. OpenSpec's archive does not capture reviewer identity, approval timestamp, or the control-impact classification of the delta. Allianz MUST wrap `/opsx:archive` with a controlled gate that captures reviewer DN, approval timestamp, and ICT-control classification, and refuses to merge deltas that touch DORA-scoped specs without that record.
- **EU AI Act Art. 9 (risk management system) and Art. 11 + Annex IV (technical documentation).** For high-risk systems, the technical documentation MUST be kept up to date "throughout the lifecycle" and MUST cover the items in Annex IV including foreseeable misuse, risk-mitigation measures, and changes to the system. OpenSpec's delta-specs cover "what changed" but do not natively map to Annex IV section identifiers. Allianz MUST maintain a fixed mapping `requirement-id → Annex IV section` and validate every archived change preserves Annex IV coverage; absence of a requirement ID in OpenSpec means this mapping is built atop file-path conventions rather than a typed identifier and requires a custom linter.
- **SR 11-7 §IV.A (effective challenge) and §V (model risk governance).** SR 11-7 expects independent review of model assumptions and limitations. OpenSpec's `/opsx:verify` is described in `OpenSpec/docs/workflows.md` as "Check implementation matches specs" — verification, not validation. The framework does not separate verification from validation, does not enforce organisational independence of the validator, and does not block archive on a failed independent-validation step. Allianz MUST configure a custom schema (`openspec schema fork`) that adds a `validation` artefact requiring sign-off by the model risk function organisationally separate from the model owner before `/opsx:archive` proceeds.
- **GDPR Art. 25 (data protection by design and by default) and Art. 35 (DPIA).** Spec changes that relax data-handling requirements (e.g., a `MUST` becoming `SHOULD` on retention or minimisation) are archived through the same path as cosmetic delta-specs. Allianz MUST add a constraint-classification step prior to archive: deltas that touch fields tagged as personal-data, consent, or retention MUST trigger a DPIA-refresh gate and MUST NOT archive without DPO acknowledgment recorded against the change folder.

## Score rationale

Score: **72/100** (Low). Evidence-for: OpenSpec treats specifications as the agreed-upon contract between humans and agents, stores them under git as Markdown with explicit RFC 2119 keywords and Given/When/Then scenarios (`OpenSpec/docs/concepts.md` "Spec Format"), separates source-of-truth specs from in-flight delta specs (`openspec/specs/` vs. `openspec/changes/<change>/specs/`), enforces explicit `ADDED`/`MODIFIED`/`REMOVED`/`RENAMED` delta operations (`OpenSpec/schemas/spec-driven/schema.yaml`), exposes `openspec validate` and `openspec status` as JSON-callable agent surfaces (`OpenSpec/docs/cli.md`), and archives every change with full proposal/design/tasks context preserved at `openspec/changes/archive/<YYYY-MM-DD>-<change>/` (`OpenSpec/docs/concepts.md` "The Archive Process") — an unusually strong substrate for the "living artefact" stance. Evidence-against: requirements have no stable identifiers and no schema beyond a Markdown-heading convention; specifications and constraints (P3 invariants) archive through the same path with no differentiated review gate (`companion/principles.md` "Specifications vs. Constraints"); none of the four convergence stop conditions from `manifesto-principles.md` §2 are instrumented; archive merges deltas without requiring evaluation reports, trace IDs, or policy-check outputs as evidence anchors; reviewer identity, approval timestamp, and independent-validation sign-off are absent from the archive record; `/opsx:verify` conflates verification with validation; no captured mapping from a requirement to its evaluations exists, which weakens the link to P8 evaluations-as-contract that the manifesto treats as inseparable from P2.
