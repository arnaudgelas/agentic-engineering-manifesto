# P7 — Context is engineered like code | **40/100**

> Review date: 2026-05-08. Manifesto: arnaudgelas/agentic-engineering-manifesto@08123c263794b5cc24dbb3e1a5897a74288026e9. Framework: OpenSpec 1.3.1. Organisation: Allianz. Industry: European insurance — DORA, Solvency II, EU AI Act, GDPR, SR 11-7.

## What OpenSpec asserts about this principle

OpenSpec asserts that project context is a structured, versionable input to agent instructions. The `openspec/config.yaml` file (`OpenSpec/openspec/config.yaml`) carries a `context` string and a per-artifact `rules` map. The `context-injection` capability (`OpenSpec/openspec/specs/context-injection/spec.md`) states that "the system SHALL inject the context field from project config into instructions for all artifacts, wrapped in XML-style `<context>` tags" and that "the system SHALL inject context content without modification, escaping, or interpretation". The `rules-injection` capability (`OpenSpec/openspec/specs/rules-injection/spec.md`) prescribes deterministic ordering — "order is `<context>` then `<rules>` then `<template>`". The `config-loading` capability (`OpenSpec/openspec/specs/config-loading/spec.md`) enforces a 50KB context-size limit, Zod schema validation, and field-by-field resilient parsing. The `instruction-loader` capability (`OpenSpec/openspec/specs/instruction-loader/spec.md`) enriches per-artifact instructions with change-specific dependency status. There is no retrieval engine, no embedding store, no rolling summary, no authority-weighted pruning, and no benchmarking of context-window usage in any source file under `OpenSpec/openspec/specs/` or `OpenSpec/src/`.

## What works

- `OpenSpec/openspec/specs/config-loading/spec.md` Requirement: "Enforce context size limit" caps the project context string at 50KB and rejects with a logged warning when "context of 51KB" is supplied — a concrete, machine-enforced context-budget bound rather than a guideline.
- `OpenSpec/openspec/specs/context-injection/spec.md` Requirement: "Format context with XML-style tags" mandates the exact byte sequence `<context>\n{content}\n</context>\n\n` and Requirement: "Context appears before template" fixes the structural placement, giving deterministic, diff-able context payloads that travel with the change in `git`.
- `OpenSpec/openspec/specs/rules-injection/spec.md` Requirement: "Validate artifact IDs during instruction loading" emits warnings for unknown artifact IDs (`"Unknown artifact ID in rules: 'unknownartifact'. Valid IDs for schema 'spec-driven': design, proposal, specs, tasks"`) and caches them so duplicates do not silently drift.
- `OpenSpec/openspec/specs/config-loading/spec.md` Requirement: "Use resilient field-by-field parsing" performs Zod-schema validation per field (`schema`, `context`, `rules`), logs a warning for invalid types (e.g. `context: 123`), and returns a sanitised `ProjectConfig` — context payloads are type-checked at load time.
- `OpenSpec/openspec/specs/schema-resolution/spec.md` Requirement: "Project-local schema resolution" defines a precedence order CLI flag → change metadata → project config → built-in default, and `OpenSpec/openspec/specs/schema-resolution/spec.md` Scenario: "Project-local schema takes precedence over package built-in" pins context-shape resolution to the project repository.
- `OpenSpec/openspec/specs/instruction-loader/spec.md` Requirement: "Template Enrichment" adds change-specific dependency status (`done` / `ready` / `blocked`) and unlocked artifacts so instruction context reflects current change graph state from `OpenSpec/openspec/changes/<change>/`.
- Context, rules, and templates live in `git`-tracked Markdown/YAML — `OpenSpec/openspec/config.yaml`, `OpenSpec/openspec/specs/<id>/spec.md`, and `OpenSpec/openspec/changes/<id>/specs/` — so context history is reviewable in the same diff workflow as code changes.
- `OpenSpec/openspec/specs/rules-injection/spec.md` Requirement: "Rules are additive to schema guidance" prevents silent override of built-in artifact instruction by config rules, removing one class of authority-weighting error at the rules-vs-schema boundary.

## Where it fails the manifesto's bar

- "Context is a first-class dependency, engineered with the same rigor as code: versioned, tested, and performance-benchmarked" (`manifesto-principles.md` §7). OpenSpec versions context (config and specs in `git`) but has no tested or performance-benchmarked context infrastructure: no source file in `OpenSpec/openspec/specs/` defines a context test suite, retrieval-latency SLO, or context-quality metric. This is convention-not-enforcement and exposes Allianz to DORA Art. 6(2) ICT-risk-management failures because context payloads driving agent reasoning are not exercised against any acceptance criterion before reaching production change folders.
- "If retrieval takes longer than the reasoning loop tolerates, context is broken infrastructure" (`manifesto-principles.md` §7 minimum bar). OpenSpec has no retrieval engine and no retrieval-time instrumentation. `OpenSpec/openspec/specs/instruction-loader/spec.md` loads templates from disk synchronously with no documented latency target. Under EU AI Act Art. 15 (accuracy, robustness, cybersecurity) Allianz cannot demonstrate that context-loading time is bounded for high-risk AI systems.
- "Stale embeddings, conflicting sources, semantic precision failures (fast retrieval of wrong artifacts), poisoned retrieval artifacts, and authority-weighting errors (an outdated ADR silently overriding current policy) are quality failures that a performance criterion does not catch" (`manifesto-principles.md` §7 minimum bar). OpenSpec has zero defences against any of these five failure modes: there is no embedding model, no staleness check, no conflict-detection rule in `OpenSpec/openspec/specs/cli-validate/spec.md`, no provenance-of-source check, and no authority weighting between `OpenSpec/openspec/config.yaml` `context` and per-artifact `rules`. Under SR 11-7 §IV.A (model risk management — sound development) Allianz cannot demonstrate inputs to model-driven decisions are quality-controlled.
- "Context quality and code quality are coupled — both must be verified, not just timed" (`manifesto-principles.md` §7 minimum bar). `OpenSpec/openspec/specs/cli-validate/spec.md` Requirement: "Bulk and filtered validation" verifies Markdown shape only — `## Why`, `## What Changes`, `### Requirement:`, `#### Scenario:` headings — and emits Zod errors. It does not verify context fidelity, source attribution, or factual currency. This is partial coverage and fails Solvency II Art. 121 (statistical quality standards) which requires data quality controls on inputs to material models.
- "Engineer explicit context budgeting: hierarchical retrieval, rolling summaries, state compaction, and authority-weighted pruning" (`manifesto-principles.md` §7). OpenSpec implements one bound — the 50KB cap in `OpenSpec/openspec/specs/config-loading/spec.md` Requirement: "Enforce context size limit" — and provides no hierarchical retrieval, no rolling summaries, no state compaction, and no authority-weighted pruning. The `<context>` block is injected verbatim and unbounded beyond 50KB. EU AI Act Art. 13 (transparency and provision of information to deployers) requires deployers to receive sufficient information to interpret outputs; an unstructured 50KB blob does not meet that bar for high-risk systems.
- "Context retrieval must be fast enough to sustain the reasoning loop" (`manifesto-principles.md` §7). OpenSpec has no SLO for context retrieval. `operational-templates/slo-table.md` defines feedback-loop closure, claim revalidation, and waiver expiry SLOs that have no counterpart in any `OpenSpec/openspec/specs/<id>/spec.md` artefact. Under DORA Art. 11 (response and recovery) Allianz cannot demonstrate measurable performance characteristics for context infrastructure.
- "If the knowledge store is polluted with bad embeddings or stale data, the agent hallucinates" (`manifesto-principles.md` §7). OpenSpec relies on `git`-tracked Markdown as the only "knowledge store" and has no detector for stale `OpenSpec/openspec/specs/<id>/spec.md` content, archived changes that contradict current specs, or `OpenSpec/openspec/changes/archive/` deltas that were not applied. `OpenSpec/openspec/specs/cli-archive/spec.md` archives by Markdown well-formedness alone. GDPR Art. 5(1)(d) (accuracy) and EU AI Act Art. 10 (data and data governance) require active accuracy controls — OpenSpec records none.
- "Authority-weighted pruning" (`manifesto-principles.md` §7). The injection pipeline in `OpenSpec/openspec/specs/context-injection/spec.md` and `OpenSpec/openspec/specs/rules-injection/spec.md` orders `<context>` before `<rules>` before `<template>` but assigns no authority weight: a contradictory rule and context line are both passed to the agent unchanged. SR 11-7 §V (effective challenge) requires explicit precedence between policy and supporting documentation; OpenSpec has none.

## Allianz-specific implications

- **DORA Art. 6(2), Art. 11 — ICT risk management and resilience testing.** OpenSpec's context infrastructure is unmeasured: no retrieval latency, no stale-data detector, no context-fidelity test in `OpenSpec/openspec/specs/`. Allianz MUST add an out-of-band context-quality test harness (staleness scan against `OpenSpec/openspec/specs/<id>/spec.md` mtimes vs change archive dates, conflict scan between `OpenSpec/openspec/config.yaml` `context` and per-artifact `rules`) and an instrumented retrieval-latency SLO before approving OpenSpec for any DORA-scoped ICT system.
- **EU AI Act Art. 10, Art. 13, Art. 15 — data governance, transparency, accuracy/robustness for high-risk AI.** The verbatim `<context>` injection in `OpenSpec/openspec/specs/context-injection/spec.md` Requirement: "Preserve context content exactly as provided" carries no provenance, currency, or source-attribution metadata. For Allianz fraud-detection or claims-triage models classified as high-risk, OpenSpec context payloads MUST be wrapped with a provenance record (source URI, retrieval timestamp, embedding/model version where applicable, integrity hash) before they are eligible to feed an agent decision.
- **Solvency II Art. 121, Art. 124 — statistical quality standards and validation.** Context entering an actuarial-model agent loop through OpenSpec is not subject to data-quality controls — `OpenSpec/openspec/specs/config-loading/spec.md` Zod validation is type-only. Allianz MUST gate any OpenSpec usage in actuarial pipelines behind an external data-quality wrapper enforcing Solvency II Art. 121 inputs (completeness, accuracy, appropriateness) and Art. 124 backtesting on context provenance.
- **SR 11-7 §IV.A, §V — sound model development and effective challenge.** The OpenSpec authority model treats `context` and `rules` as additive strings (`OpenSpec/openspec/specs/rules-injection/spec.md` Requirement: "Rules are additive to schema guidance"). For Allianz's US-supervised entities operating under SR 11-7, conflicting policy in `<rules>` and supporting context in `<context>` MUST be resolved by a precedence layer (organisation policy > business-unit policy > project context) implemented outside OpenSpec; the framework provides none.
- **GDPR Art. 5(1)(d), Art. 25 — accuracy and data protection by design.** OpenSpec context can carry personal-data references in `OpenSpec/openspec/config.yaml` `context` strings without redaction, masking, or DSAR linkage. Allianz MUST forbid personal data in OpenSpec context fields by repository hook and add a static-analysis check on `OpenSpec/openspec/config.yaml` and `OpenSpec/openspec/specs/<id>/spec.md` before commit, given GDPR Art. 25 by-design obligations and the absence of any redaction control in OpenSpec source artefacts.

## Score rationale

Score: **40/100** (High). Evidence-for: OpenSpec versions context as `git`-tracked YAML and Markdown (`OpenSpec/openspec/config.yaml`, `OpenSpec/openspec/specs/<id>/spec.md`), enforces deterministic XML-bracketed injection (`OpenSpec/openspec/specs/context-injection/spec.md`, `OpenSpec/openspec/specs/rules-injection/spec.md`), caps payload size at 50KB with a machine-enforced bound (`OpenSpec/openspec/specs/config-loading/spec.md` Requirement: "Enforce context size limit"), validates the configuration shape with Zod, and warns on unknown artifact IDs in rules; this satisfies the "versioned" half of the minimum bar at the configuration layer and provides one concrete budget bound. Evidence-against: OpenSpec implements none of the five quality failure modes the minimum bar names — staleness, conflicting sources, semantic precision, poisoning, authority weighting — and has no retrieval engine, no embedding store, no benchmarked retrieval-time SLO, no rolling summary, no state compaction, no hierarchical retrieval, no authority-weighted pruning, no test suite for context, and no provenance metadata on injected payloads. Verbatim, unscored, additive injection of `<context>` and `<rules>` (`OpenSpec/openspec/specs/rules-injection/spec.md` Requirement: "Rules are additive to schema guidance") is incompatible with SR 11-7 §V effective-challenge precedence and Solvency II Art. 121 statistical-quality controls; under EU AI Act Art. 13 and DORA Art. 6(2) the unscored payload would not constitute sufficient deployer information for a high-risk Allianz system. The score lands at the lower edge of the High band because structural rigor at the configuration layer is real and machine-checked, but the testable, benchmarked, quality-controlled context-as-code substance the manifesto requires is structurally absent.
