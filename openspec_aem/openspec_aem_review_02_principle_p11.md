# P11 — Optimize economics of intelligence | **18/100**

> Review date: 2026-05-08. Manifesto: arnaudgelas/agentic-engineering-manifesto@08123c263794b5cc24dbb3e1a5897a74288026e9. Framework: OpenSpec 1.3.1. Organisation: Allianz. Industry: European insurance — SR 11-7, DORA, EU AI Act, GDPR, Solvency II.

## What OpenSpec asserts about this principle

OpenSpec makes no assertion about the economics of intelligence. The framework is a CLI for spec-driven authoring; it does not select, route, meter, or cost models. The complete supported-tools set in `OpenSpec/docs/supported-tools.md` enumerates editor integrations (`amazon-q`, `antigravity`, `auggie`, `bob`, `claude`, `cline`, `codex`, `forgecode`, `codebuddy`, `continue`, `costrict`, `crush`, `cursor`, `factory`, `gemini`, `github-copilot`, `iflow`, `junie`, `kilocode`, `kimi`, `kiro`, `opencode`, `pi`, `qoder`, `lingma`, `qwen`, `roocode`, `trae`, `windsurf`) but treats each as an opaque opener — no model identifier, model tier, token-budget, or per-task routing rule is declared. The telemetry contract in `OpenSpec/openspec/specs/telemetry/spec.md` Requirement "Privacy-preserving event design" states the system "SHALL NOT include command arguments, file paths, project names, spec content, error messages, or IP addresses in telemetry events", and Requirement "Command execution tracking" emits only `command` and `version`. Cost-per-task, cost-per-outcome, model-mix, and inference spend are absent from `OpenSpec/openspec/`, `OpenSpec/src/`, and `OpenSpec/docs/` in their entirety.

## What works

- `OpenSpec/openspec/config.yaml` provides a single declarative `context` block and tool rules that an upstream router consumes once per session, which keeps prompt context engineering decoupled from per-task model selection and avoids per-call context bloat in the consuming agent harness.
- The delta-only artefact convention in `OpenSpec/openspec/specs/openspec-conventions/spec.md` Requirement "Change proposals SHALL store only the additions, modifications, and removals to specifications, not complete future states" reduces token volume sent to whichever model the host harness selects, lowering inference cost on each `/opsx:propose` and `/opsx:apply` invocation against a brownfield codebase.
- `OpenSpec/openspec/specs/cli-validate/spec.md` Requirement "Bulk and filtered validation" runs a deterministic Zod-based structural check (`openspec validate --all --strict --json`) with no model call, shifting cheap correctness checks off the inference path before any agent is invoked.
- `OpenSpec/openspec/specs/openspec-conventions/spec.md` Requirement "OpenSpec conventions SHALL keep specs lightweight by default and scale rigor only when risk or coordination complexity demands it" matches the manifesto's "When governance overhead exceeds the value of the work, that is a signal to simplify" minimum-bar logic at the documentation layer.
- `OpenSpec/openspec/specs/cli-archive/spec.md` archives changes into `openspec/changes/archive/` so retrieval scope shrinks to active changes, which bounds the corpus a downstream model retrieves at proposal time.

## Where it fails the manifesto's bar

- "Build a dynamic routing layer. Route simple tasks to fast, cheap models. Reserve expensive, high-reasoning models for complex orchestration and critical decisions" (`manifesto-principles.md` §11). OpenSpec does not provide a routing layer, a model registry, or a tier classifier in any source file under `OpenSpec/src/` or `OpenSpec/openspec/specs/`. Model selection is delegated wholesale to the host editor (`OpenSpec/docs/supported-tools.md`), making model choice a configuration constant of the host, not a runtime decision of OpenSpec. This is a scope gap and is flagged here against EU AI Act Art. 9(2) (risk management of foundation-model selection for high-risk AI systems used by Allianz).
- "Model choice is a runtime decision, not a configuration constant" (`manifesto-principles.md` §11 minimum bar). `OpenSpec/openspec/config.yaml` schema (`schema: spec-driven`) and `OpenSpec/openspec/specs/global-config/spec.md` define no model field; `OpenSpec/openspec/specs/cli-init/spec.md` `--tools` flag binds an editor identifier, not a model. By the manifesto's own minimum bar, this is overspending. SR 11-7 §III (model risk) requires Allianz to evidence the rationale for the chosen model per task class — OpenSpec records none.
- "Optimize total cost of correctness — not just inference cost, but the full cycle: `inference + verification + governance overhead + incident remediation`" (`manifesto-principles.md` §11). OpenSpec has no cost field, no incident counter, and no governance-overhead measure. `OpenSpec/openspec/specs/telemetry/spec.md` Requirement "Privacy-preserving event design" actively excludes all the fields needed to compute total-cost-of-correctness. DORA Art. 28 (ICT third-party risk) requires Allianz to track concentration and cost exposure to model providers; OpenSpec produces no such data.
- "Track cost per task, cost per outcome, and cost per quality unit" (`manifesto-principles.md` §11). No file in `OpenSpec/openspec/specs/` defines a task-cost, outcome-cost, or quality-unit metric. `OpenSpec/openspec/specs/telemetry/spec.md` Requirement "Command execution tracking" emits only `{ command, version }` and `OpenSpec/openspec/specs/cli-feedback/spec.md` does not record cost. Solvency II Art. 41 (system of governance) and Art. 44 (risk management) require quantitative tracking of operational cost drivers tied to risk; OpenSpec records zero.
- "When governance overhead exceeds the value of the work, that is a signal to simplify, not to add more governance" (`manifesto-principles.md` §11). OpenSpec records no governance-overhead measure, so the simplification signal is structurally unobservable. `OpenSpec/openspec/specs/opsx-verify-skill/spec.md` Requirement "Verification Report Format" produces CRITICAL/WARNING/SUGGESTION counts but does not relate them to cost or value delivered. Under EU AI Act Art. 17 (quality management) Allianz cannot demonstrate the proportionality of governance to value.
- "treating cross-model disagreement on shared artifacts as an observable quality signal rather than a coordination annoyance" (`manifesto-principles.md` §11). OpenSpec has no concept of cross-model disagreement, no provenance field on a generated artefact, and no comparator. `OpenSpec/openspec/specs/opsx-verify-skill/spec.md` runs a single agent against an implementation. SR 11-7 §IV.A (model validation including challenger models) requires effective challenge across alternative models — OpenSpec exposes no hook for it.
- "Making shared architectural decisions explicit in the knowledge base rather than relying on implicit prompt conventions" (`manifesto-principles.md` §11). `OpenSpec/openspec/config.yaml` `context:` is a free-text block; `OpenSpec/openspec/specs/context-injection/spec.md` injects rules into editor tool files but does not constrain which model receives which architectural fact. Under DORA Art. 16 (ICT-risk-management framework) Allianz cannot evidence which model executed which decision.
- "Routing semantically related tasks through the same model tier when consistency matters more than cost" (`manifesto-principles.md` §11). OpenSpec defines no tier, no routing predicate, and no consistency-vs-cost selector in any source under `OpenSpec/src/cli/` or `OpenSpec/src/commands/`. EU AI Act Art. 15 (accuracy, robustness, cybersecurity) requires consistency evidence per task class for high-risk AI — OpenSpec produces none.

## Allianz-specific implications

- Solvency II Art. 41 (system of governance) and Art. 44 (risk management) require Allianz to evidence operational and model-risk cost drivers. OpenSpec produces zero cost telemetry per `OpenSpec/openspec/specs/telemetry/spec.md`. Allianz MUST wrap OpenSpec invocations with a host-harness cost meter that records foundation-model identifier, token in/out, and per-change spend, and pipes that into the existing Solvency II ORSA cost-tracking ledger before adopting OpenSpec for any artefact in internal-model scope.
- DORA Art. 28 (ICT third-party risk) and Art. 29 (concentration risk) require Allianz to monitor concentration on a single foundation-model provider. The 29-tool list in `OpenSpec/docs/supported-tools.md` opaquely delegates model choice to the editor. Allianz MUST publish an internal allow-list of editor+model pairings approved per use case, with a concentration-cap policy, before extending OpenSpec across business units.
- SR 11-7 §IV.A (model validation, including effective challenge using challenger models) requires Allianz to validate model choice for material decisions. `/opsx:verify` (`OpenSpec/openspec/specs/opsx-verify-skill/spec.md`) runs a single model and does not evidence challenger-model results. Allianz MUST require dual-model regeneration of `/opsx:propose` artefacts for any change touching SR 11-7 in-scope systems and store both outputs in the change folder.
- EU AI Act Art. 9(2) (risk management) and Art. 15 (accuracy, robustness, cybersecurity) require documented rationale for model selection per high-risk task class. `OpenSpec/openspec/config.yaml` has no model field. Allianz MUST extend the host harness to write a `model-decision.json` (foundation model identifier, version, tier, rationale, alternatives evaluated) into every `openspec/changes/<id>/` folder so the change package is self-describing for AI-Act technical-documentation purposes (Art. 11, Annex IV §2(b)).
- DORA Art. 17 (ICT-related incident management) requires linkage between incidents and the cost of remediation. `OpenSpec/openspec/specs/cli-feedback/spec.md` records no incident or remediation cost. Allianz MUST integrate OpenSpec change folders with its operational-incident register so each archived change carries a back-reference to any incident triggered post-deployment, with measured remediation hours and inference cost.

The 18/100 reflects two narrow positives (token-volume reduction via deltas, cheap structural validation) against eight P11 minimum-bar requirements that are wholly absent.
