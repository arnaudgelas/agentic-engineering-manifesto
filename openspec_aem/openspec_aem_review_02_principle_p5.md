# P5 — Autonomy is a tiered budget | **38/100**

## What OpenSpec asserts about this principle

OpenSpec asserts a human-and-AI co-authoring model in which AI assistants generate planning artefacts (`proposal.md`, `specs/`, `design.md`, `tasks.md`) and execute implementation tasks under human direction, but it does not assert a tiered autonomy model, a permission system, a policy envelope, or any machine-enforced authority gate. `OpenSpec/README.md` states "Agree before you build — human and AI align on specs before code gets written" and `OpenSpec/docs/concepts.md:Human + Agent Collaboration` describes the loop as "Human provides intent, context, and constraints" with the agent drafting and humans reviewing. The `/opsx:apply` command (`OpenSpec/docs/opsx.md` lines 205–209) "works through tasks, checking them off as you go" without any tier classification, blast-radius assessment, kill-switch, or evidence-bundle gate. The `OpenSpec/openspec/config.yaml` rules block (`OpenSpec/docs/opsx.md:90–98`) lists advisory items such as "Include rollback plan" — these are content prompts to the AI, not enforced constraints on agent action.

## Tier Assessment

**What actions OpenSpec takes autonomously (without any human step).** Within an OpenSpec session, the AI assistant autonomously: (a) generates `proposal.md`, `specs/**/*.md` deltas, `design.md`, and `tasks.md` from a one-line prompt via `/opsx:propose` or `/opsx:ff` (`OpenSpec/docs/opsx.md:181–203`); (b) edits files in the working tree during `/opsx:apply` (`OpenSpec/docs/opsx.md:205–209`); (c) re-orders, fast-forwards, or marks tasks complete with no in-tool confirmation step; (d) writes archive content into `openspec/changes/archive/` via `/opsx:archive` (`OpenSpec/docs/cli.md` archive section). Every autonomous edit lands in the local working copy where the user holds final commit authority — but OpenSpec itself imposes no per-step approval, no diff-review checkpoint, and no tool-call authorisation list.

**What requires human approval within OpenSpec's lifecycle.** Nothing inside OpenSpec is structurally gated. Human approval is implicit and external: the human reads the artefacts the AI produced, edits them in their editor if desired, and runs `git commit` themselves. `OpenSpec/docs/cli.md:Human-Only Commands` lists commands "designed for human use in a terminal" — this distinguishes invocation context, not approval authority. The "Review-friendly. A change folder is easy to review" claim in `OpenSpec/docs/concepts.md:345` is a usability assertion; it is not an enforced gate that blocks `/opsx:apply` from proceeding without sign-off.

**What is never autonomous under OpenSpec's current design.** Production deployment, `git push`, schema migration, infrastructure mutation, and any action outside the working tree are out of scope for OpenSpec — `OpenSpec/docs/concepts.md` and `OpenSpec/docs/workflows.md` confine OpenSpec's surface to local artefact authoring and task execution. Schema customisation requires `openspec schema fork` (`OpenSpec/docs/customization.md:309–325`) which is a human CLI invocation. *[Scope gap]* — OpenSpec is a planning + apply layer, not a deployment or governance system; production action gating is outside its stated scope, but the absence of an internal tier model is itself a P5 finding because P5 governs the agent's authority within the framework's lifecycle.

**Tier determination.** OpenSpec operates structurally at **Tier 1 (Observe)** for planning artefacts (the human reads and revises before any code change) and at **Tier 2 (Branch) by convention only** for `/opsx:apply` when the user happens to be on a feature branch. The manifesto defines Tier 2 as "Agents write to isolated branches. Humans approve merges. Blast radius: contained" (`manifesto-principles.md:209–210`). OpenSpec does not enforce branch isolation, does not detect whether `/opsx:apply` is running on `main`, does not block edits to protected paths, and does not produce an evidence bundle to gate a merge approval. The Tier 2 claim is therefore nominal — the structural evidence (no enforcement) places OpenSpec at Tier 1 with optional uncontrolled escalation to Tier 2 by user discretion.

**Oversight pattern.** OpenSpec instantiates **HITL asynchronous** for the artefact-authoring loop: the AI produces `proposal.md`, the human reads it after the fact and edits it in place. The manifesto's P5 minimum bar for HOTL — "the irreversibility window for a HOTL-designated action class has not been measured and confirmed to exceed the sum of monitoring detection, notification, assessment, and intervention time" (`manifesto-principles.md:362–365`) — is not met because OpenSpec measures no irreversibility window at all. The HOLL minimum bar — "the per-action evidence record is not sufficient to reconstruct accountability from logs alone" (`manifesto-principles.md:367–370`) — fails because OpenSpec logs no per-action evidence record beyond the artefact filesystem state. OpenSpec does not instantiate HOTL, HOLL, or EDL.

**Tier 4 prerequisites (if claimed).** OpenSpec makes no Tier 4 claim and supports none. Against the four prerequisites from `manifesto-principles.md:249–251` and `governance/governance-integration-note.md:18`:
- Machine-enforced policy envelope — **Absent**. No envelope exists in `OpenSpec/openspec/config.yaml`; the `rules` block injects text into prompts (`OpenSpec/docs/opsx.md:121–124`) and is not an enforcement layer.
- Passing control evaluations — **Absent**. No control evaluations are defined; `OpenSpec/test/` covers CLI behaviour, not governance controls.
- Instrumented governance observability — **Absent**. No telemetry surfaces stale evidence, drift, or rubber-stamping signals; `OpenSpec/src/telemetry/` (referenced in `OpenSpec/src/` listing) records CLI usage, not governance state.
- Active rubber-stamping detection — **Absent**. No reviewer-agreement or override-rate metric is captured anywhere in OpenSpec's artefacts.

**Phase × tier compatibility.** Per `manifesto-principles.md:272–276`, Tier 2 requires Phase 4 ("Verification gates operational; blast radius is contained"). OpenSpec provides no verification gates beyond `openspec validate` (`OpenSpec/docs/cli.md` validate section) which checks artefact structural conformance, not behavioural correctness. A team relying on OpenSpec alone has the AEM Phase characteristics of Phase 1–3 (no evaluation suite, no evidence bundles, no governance infrastructure). The maximum permissible tier per the phase × tier table is therefore **Tier 1 only for governed production work**, not the Tier 2 OpenSpec is sometimes used at by convention.

**What prevents higher tiers.** To safely operate at Tier 2, OpenSpec would need to (i) enforce branch isolation as a structural precondition for `/opsx:apply`, (ii) emit an evidence bundle conforming to `manifesto-done.md` per change, and (iii) gate `/opsx:archive` on policy-check outputs. To support Tier 3, OpenSpec would additionally need a per-change rollback record, a named human signoff captured as data (not as a `git commit` author line), and an integration with deployment that produces a deployment ID. Tier 4 is structurally unreachable for OpenSpec because the framework is a planning + apply layer with no machine-enforced envelope and no governance observability surface.

## What works

- The artefact dependency graph (`OpenSpec/docs/opsx.md:422–449`) — `proposal → {specs, design} → tasks → apply` — provides a structural progression where the AI cannot fast-forward to `/opsx:apply` until upstream artefacts exist, giving the human a natural read-checkpoint between AI planning and AI execution.
- `openspec validate` (`OpenSpec/docs/cli.md` validate command) enforces artefact-schema conformance before `/opsx:archive`, which is a low-grade structural gate that catches malformed changes — it does not gate on semantic correctness but it does prevent shipping artefacts that fail format checks.
- `OpenSpec/docs/cli.md:Human vs Agent Commands` distinguishes which commands are "designed for human use" versus "agent/script use via JSON output", a partial separation of concerns that supports a HITL asynchronous review pattern when humans choose to read artefacts before committing.
- The `rules` injection mechanism (`OpenSpec/openspec/config.yaml`, documented at `OpenSpec/docs/opsx.md:121–124`) lets a team write project-specific advisory rules (e.g., "Include rollback plan") that are surfaced to the AI in every artefact-generation prompt, providing a soft policy channel that bounds agent behaviour at content level.
- `/opsx:archive` (`OpenSpec/docs/cli.md` archive section) preserves the change folder under `openspec/changes/archive/` with proposal, design, and tasks intact, providing a post-action audit trail for the change as authored.
- Schema customisation via `openspec schema fork` (`OpenSpec/docs/customization.md:309–325`) lets a regulated team add a `review` artefact that requires explicit content before `tasks` can be authored, giving downstream teams a hook to insert a human-review artefact into the dependency chain.

## Where it fails the manifesto's bar

- "Grant permissions by risk tier, least privilege, and blast-radius limits" (`manifesto-principles.md:200–201`). OpenSpec defines no risk tier for any change. `/opsx:propose add-payment-processor` and `/opsx:propose fix-typo` follow identical artefact paths with identical agent authority. Convention-not-enforcement: no signal in `OpenSpec/openspec/config.yaml` triggers different oversight. For Allianz, this fails Solvency II Art. 121(1) — internal-model change governance requires major-versus-minor classification before model change, and OpenSpec offers no classification step.
- "Tier 1 — Observe. Agents analyze and propose. Blast radius: none. … Tier 2 — Branch. Agents write to isolated branches. Humans approve merges. Blast radius: contained" (`manifesto-principles.md:207–210`). OpenSpec's `/opsx:apply` writes directly to the user's working tree on whatever branch is checked out. There is no branch-isolation precondition, no merge-approval evidence, and no enforced separation between observation and branch action. Advisory-only: the Tier 2 model is implementable by user discipline but not enforced by OpenSpec. For Allianz, this fails DORA Art. 9(2) — ICT change management requires approved processes for the management of changes to ICT systems, and a framework that lets agents edit production-relevant repositories without enforced branch isolation does not satisfy that requirement.
- "If an agent can invoke tools that have not been explicitly authorized for its operating tier, the tier model is nominal. Tool access is part of the permission model — not a separate concern" (`manifesto-principles.md:243–247`). OpenSpec defines no tool manifest, no per-tier tool whitelist, and no enforcement that the AI's tool access matches the change's risk class. Absent. For Allianz, this fails EU AI Act Art. 14(4)(b) — human oversight measures must enable the deployer to "remain aware of … the possible tendency of automatically relying or over-relying on the output", and an agent operating without an authorisation boundary on its tool calls produces output a human cannot bound the source of.
- "If you cannot reconstruct an agent's reasoning at any tier, your autonomy model has failed" (`manifesto-principles.md:240–241`). OpenSpec preserves the artefact filesystem but does not record per-action tool calls, decisions, evaluation results, or near-misses. The archive contains *what* was authored, not *why* each artefact-edit decision was made. Absent. For Allianz, this fails Solvency II Art. 124 (validation standards) — the validation function must independently assess the reasoning behind model outputs, and OpenSpec's archive does not surface that reasoning.
- "Tier 4 is not Tier 3 with the human removed. … This only holds when the policy envelope is machine-enforced (not merely documented), control evaluations confirm the governance system itself works (P8), governance observability is instrumented and alerting on stale evidence and drift (P9), and rubber-stamping detection is active (P12). Without these prerequisites, Tier 4 is ungoverned production autonomy" (`manifesto-principles.md:224–230`). OpenSpec implements none of the four Tier 4 prerequisites. Absent. The risk is not that OpenSpec claims Tier 4 — it does not — but that an Allianz team adopting OpenSpec without an external envelope mechanism cannot evolve toward higher tiers; the framework leaves the prerequisites unaddressed. This fails EU AI Act Art. 14(4)(a) — oversight design must allow natural persons "to properly understand the relevant capacities and limitations of the high-risk AI system".
- "Phase maturity is a prerequisite for autonomy tier" (`manifesto-principles.md:253–255`). OpenSpec does not record team phase, does not gate command availability on phase, and does not provide a phase-detection mechanism. Absent. For Allianz, this fails EIOPA Opinion on AI Governance and Risk Management (2021) §3.4 — proportionality of governance to AI maturity is a supervisory expectation, and a framework with no phase gate cannot calibrate proportionality.
- "If the irreversibility window for a HOTL-designated action class has not been measured and confirmed to exceed the sum of monitoring detection, notification, assessment, and intervention time, HOTL is not providing oversight — it is providing the appearance of oversight" (`manifesto-principles.md:362–365`). OpenSpec measures no irreversibility window. `/opsx:apply` writes file edits whose reversibility depends on `git` discipline external to OpenSpec, not on a measured window. Absent. For Allianz, this fails DORA Art. 11 (response and recovery) — incident-response readiness requires measured recovery times, and an apply mechanism with no measured reversibility window contradicts the Pillar 2 ICT operational resilience standard.
- "If an agent can invoke tools that have not been explicitly authorized for its operating tier, the tier model is nominal" (`manifesto-principles.md:243–247`) — combined with the tier-containment minimum bar at P4 — "An orchestrator cannot delegate actions to specialist agents that exceed its own authorized autonomy tier" (`manifesto-principles.md:191–194`). OpenSpec runs inside the host AI assistant (`claude`, `cursor`, `codex`, etc., per `OpenSpec/docs/supported-tools.md`) and inherits whatever tool authority that assistant holds. OpenSpec does not constrain the host's tool calls during `/opsx:apply`. Convention-not-enforcement. For Allianz, this fails SR 11-7 §V (model implementation and use) — model use boundaries must be enforced, not delegated to a heterogeneous set of host assistants whose authorisation surfaces differ.

## Allianz-specific implications

- Solvency II Art. 121 (internal model change policy) requires the undertaking to classify each change as major or minor before implementation, with major changes triggering supervisory pre-approval. OpenSpec's uniform artefact path through `/opsx:propose → /opsx:apply → /opsx:archive` provides no classification step and no supervisory-pre-approval gate. Allianz must layer a change-classification artefact (via `openspec schema fork` per `OpenSpec/docs/customization.md:309–325`) into every Solvency II model-scope change, with the classification recorded as a structured field that downstream automation can read and gate `/opsx:archive` on. Without this, every OpenSpec-authored change to an SCR-relevant repository is a Solvency II compliance breach risk.
- EU AI Act Art. 14(4)(a)–(e) requires human oversight measures for high-risk AI systems that enable natural persons to remain aware of automation bias, intervene, and disregard the output. For Allianz's underwriting and claims agents (high-risk per Annex III §5(b)), the manifesto caps autonomy at Tier 1. OpenSpec's lack of an enforced tier model means a development team using OpenSpec to author and apply changes to a high-risk system cannot demonstrate to BaFin or to the EIOPA-channeled supervisor that the agent's authority during development was bounded. Allianz must wrap OpenSpec invocations with an external authorisation layer that records, per `/opsx:apply` invocation, the tier the action was authorised at and the named accountable person.
- DORA Art. 9(2) (ICT risk management framework) and Art. 28(2) (ICT third-party risk) require approved change-management processes and oversight of third-party ICT components. The host AI assistants OpenSpec runs inside (`OpenSpec/docs/supported-tools.md` lists 25+ tools) are ICT third parties for DORA purposes when they author changes to Allianz repositories. OpenSpec's convention-not-enforcement model does not produce the per-action authorisation evidence DORA Art. 28 expects. Allianz must record every host-assistant invocation, the tool manifest active during the invocation, and the approval status of each tool against the Allianz-approved third-party register, and gate `/opsx:archive` on that record's presence.
- SR 11-7 §IV.A (model risk management — model development) requires a controlled development environment with documented authority over model changes. OpenSpec records artefact edits but does not record the agent's authority to make them. Allianz's MRM function cannot derive from OpenSpec's archive whether a given change was within the developer's documented authority or exceeded it. Allianz must capture, alongside each archived change, a structured authority record naming the developer, the model in scope, and the authority class — sourced from Allianz's authority register, not from `git` author metadata.
- GDPR Art. 22 (automated individual decision-making) prohibits decisions based solely on automated processing that produce legal or similarly significant effects, except under narrow exceptions. For agents Allianz develops with OpenSpec that touch underwriting, pricing, or claims decisions on personal lines, the lack of an enforced Tier 1 ceiling during development creates a path where a future `/opsx:apply` autonomously rewires a decision boundary in code without human pre-review of the boundary change as a boundary change. Allianz must define an Art. 22-relevant code path register and gate `/opsx:apply` against it via a fork of the spec-driven schema that requires a `human-decision-boundary-review` artefact for any change touching the register.

## Score rationale

Score: **38/100** (Critical). Evidence-for: OpenSpec provides a structural artefact-dependency graph (`OpenSpec/docs/opsx.md:422–449`) that creates natural read-checkpoints between planning and apply; `openspec validate` enforces artefact-schema conformance; the archive at `openspec/changes/archive/` preserves the as-authored content of each change; the schema-fork mechanism (`OpenSpec/docs/customization.md:309–325`) is an extensibility surface that a downstream team can use to inject a human-review artefact; the human-versus-agent CLI distinction (`OpenSpec/docs/cli.md:Human-Only Commands`) supports a HITL asynchronous oversight pattern when humans choose to read artefacts before committing. Evidence-against: OpenSpec defines no risk-tier classification, no permission system, no tool authorisation list, no policy envelope, no per-action evidence record, no irreversibility-window measurement, no rubber-stamping detection, no governance observability, and no phase × tier compatibility check; the framework operates structurally at Tier 1 with uncontrolled convention-only escalation to Tier 2; none of the four Tier 4 prerequisites from `manifesto-principles.md:249–251` are addressed; the tier model required by P5 — and the EU AI Act Art. 14, DORA Art. 9, Solvency II Art. 121, SR 11-7 §IV.A, and GDPR Art. 22 obligations Allianz must meet — is absent from OpenSpec's enforced surface and must be supplied externally for Allianz to use OpenSpec safely on regulated systems.
