# P9 — Observability covers reasoning | **18/100**

> Review date: 2026-05-08. Manifesto: arnaudgelas/agentic-engineering-manifesto@08123c263794b5cc24dbb3e1a5897a74288026e9. Framework: OpenSpec 1.3.1. Organisation: Allianz. Industry: European insurance and financial services — SR 11-7, DORA, EU AI Act, GDPR, Solvency II.

## What OpenSpec asserts about this principle

OpenSpec asserts that the change archive functions as the audit surface: "**Audit trail.** The archive preserves the full context of every change — not just what changed, but the proposal explaining why, the design explaining how, and the tasks showing the work done." (`docs/concepts.md` "Why Archive Matters", line 685) and "Preserves all artifacts for audit trail" (`docs/commands.md` line 462). Runtime telemetry is defined exclusively in `openspec/specs/telemetry/spec.md`, whose "Command execution tracking" requirement states that the system "SHALL send a `command_executed` event to PostHog when any CLI command executes, including only the command name and OpenSpec version as properties" and whose "Privacy-preserving event design" requirement states the system "SHALL NOT include command arguments, file paths, project names, spec content, error messages, or IP addresses in telemetry events". OpenSpec defines no agent reasoning trace, no tool-call log, no decision-chain artefact, and no governance-state instrumentation in any file under `OpenSpec/openspec/specs/` or `OpenSpec/docs/`.

## Does OpenSpec's observability cover reasoning or only execution?

**Short answer: neither in the manifesto's sense — OpenSpec instruments only CLI command-name occurrences and a Markdown change archive; it does not instrument agent reasoning, agent execution, or governance state.**

What OpenSpec logs and instruments:

- **PostHog `command_executed` events** (`openspec/specs/telemetry/spec.md`, Requirement: "Command execution tracking"). The event payload is exactly `{ command, version }` plus an anonymous UUID (`openspec/specs/telemetry/spec.md`, Requirement: "Anonymous user identification"). Arguments, file paths, project names, spec content, and error messages are explicitly excluded by the "Privacy-preserving event design" requirement. The event records *that* a command name fired; it cannot record *why* an agent took a decision because the agent's decision data is filtered out by design.
- **The Markdown change archive** (`docs/concepts.md` "Why Archive Matters", `openspec/specs/cli-archive/spec.md`). The archive preserves `proposal.md`, `design.md`, `tasks.md`, and the delta-spec files of each completed change. This is a human-authored narrative of *why* a *change to a specification* was made; it is not a record of *why an agent took a runtime action*.
- **Verification reports from `/opsx:verify`** (`openspec/specs/opsx-verify-skill/spec.md`, Requirement: "Verification Report Format"). The skill produces "CRITICAL / WARNING / SUGGESTION" output with a "specific, actionable fix recommendation" (`docs/commands.md` line 336). Reports are produced on demand and not stored as a trace artefact, and they "Does not block archive" (`docs/commands.md` line 336).
- **`openspec validate --json`** (`openspec/specs/cli-validate/spec.md`, Requirement: "JSON output schema for bulk validation"). Returns `{ items[], summary, version }` describing structural conformance only.

What the manifesto's P9 minimum bar requires for reasoning-level observability and what OpenSpec lacks:

- The minimum bar states "*If you cannot answer 'why did this happen' from traces alone, you are not instrumented*" (`manifesto-principles.md` §9). OpenSpec's PostHog event explicitly excludes everything that would let a reader answer "why" — arguments, file paths, project names, spec content, and error messages are filtered out by the "Privacy-preserving event design" requirement. The archive answers "why was this change proposed" through human-authored prose, not "why did an agent select this tool, retrieve this claim, or output this decision".
- P9 demands instrumentation of "decisions, tool calls, policy violations, memory retrievals, cost per task, and near-misses" (`manifesto-principles.md` §9). No file under `OpenSpec/openspec/specs/` defines any of these constructs. There is no decision log, no tool-call log, no policy-violation feed, no memory-retrieval trace, no cost-per-task counter, and no near-miss register.

The AEM execution trace described in `governance/integrated-audit-trail.md` is **not producible** from OpenSpec's output:

- **Trace IDs spanning spec → design → plan → execute → verify → validate → observe → learn → govern** — Absent. `openspec/specs/cli-archive/spec.md` ties artefacts to a change folder name, not to a `trace_id`. The PostHog event ID is per CLI invocation and is not linkable to a specification, action, or evidence record.
- **Per-action tool calls, decisions, evaluation results, rollbacks, near-misses** — Absent. `/opsx:verify` (`openspec/specs/opsx-verify-skill/spec.md`) is an agent-run skill whose execution is not captured to a structured trace; no rollback or near-miss artefact exists in `OpenSpec/openspec/specs/`.
- **OpenTelemetry-compatible identifiers** — Absent. `openspec/specs/telemetry/spec.md` uses PostHog with `flushAt: 1` and an anonymous UUID. There is no W3C Trace Context, no OpenTelemetry span, and no mention of OTLP in any source file.
- **Replayable from trace ID + agentic provenance record + tool manifest + composite state** — Absent. OpenSpec defines none of these inputs: there is no agentic provenance record artefact, no tool manifest construct, and no composite-state hash anywhere under `OpenSpec/openspec/specs/`.

Governance-state observability (the second minimum-bar paragraph in P9) is **not instrumented**:

- "Stale evidence in active bundles surfaced without manual audit using the freshness rules" — Absent. OpenSpec has no evidence-bundle construct and no freshness rule. `openspec/specs/cli-archive/spec.md` archives on Markdown well-formedness alone.
- "Controls in failed/waived state with no recorded resolution timeline or expiry" — Absent. There is no control-state record, no waiver register, and no expiry mechanism in `OpenSpec/openspec/specs/`. SLOs 28–30 of `operational-templates/slo-table.md` (waiver review cadence, auto-expire, compensating-control review) have no counterpart command or schema.
- "Accountability ownership gaps — active production components with no named, current owner" — Absent. The agent-inventory schema (`operational-templates/agent-inventory-schema.md`) has no counterpart in OpenSpec; no file under `OpenSpec/openspec/specs/` records owners of active components.
- "Rubber-stamping patterns — review-time distribution anomalies and approval-without-trace events" — Absent. `adoption/metrics.md` rubber-stamping detection is unimplemented; `/opsx:verify` produces a single agent-run review with no distribution log of reviewer agreement, override rate, or review latency.
- "Model, prompt, or tool manifest changes that have not triggered an evaluation re-run" — Absent. OpenSpec has no foundation-model identifier field, no prompt manifest, and no tool manifest under `OpenSpec/openspec/specs/`. `openspec/specs/cli-archive/spec.md` does not condition archive on any model/prompt/tool integrity check.

The specific gap between what OpenSpec records and what a "why did this happen" query requires is total at the runtime layer: OpenSpec records the literal CLI command name and a human-authored change narrative; it does not record the agent's inputs, the agent's retrievals, the agent's intermediate decisions, the agent's tool calls, the agent's outputs, or the policy state at the time of each action. A regulator asking BaFin's "show me the audit trail for the action" question (per the worked walkthrough in `governance/integrated-audit-trail.md` §3) cannot be answered from any OpenSpec artefact.

## What works

- `docs/concepts.md` "Why Archive Matters" (line 685) preserves a per-change Markdown audit narrative — `proposal.md` (why), `design.md` (how), `tasks.md` (steps), and the delta-spec files — co-located in `changes/archive/<id>/` per `openspec/specs/cli-archive/spec.md` Requirement: "Archive directory structure", giving a defensible spec-change record.
- `openspec/specs/cli-archive/spec.md` Requirement: "Pre-archive validation" enforces structural validation of the change before archive, ensuring the archived narrative is well-formed Markdown that a downstream auditor can parse mechanically.
- `openspec/specs/telemetry/spec.md` Requirement: "Anonymous user identification" generates a stable UUID stored in global config so repeated `command_executed` events from the same workstation are linkable, providing a minimal cross-session join key.
- `openspec/specs/opsx-verify-skill/spec.md` Requirement: "Verification Report Format" prescribes a CRITICAL/WARNING/SUGGESTION priority scheme with a "specific, actionable fix recommendation" field, producing a structured-text artefact that a reviewer can attach to the change folder.
- `openspec/specs/cli-validate/spec.md` Requirement: "JSON output schema for bulk validation" emits a stable `{ items[], summary, version }` shape consumable by external CI dashboards, giving structural validation a machine-readable observability surface.
- `openspec/specs/cli-feedback/spec.md` Requirement: "Issue metadata" attaches OpenSpec CLI version, platform, and submission timestamp to each feedback issue, providing a small per-event provenance footprint for tool-quality signals.

## Where it fails the manifesto's bar

- "*If you cannot answer 'why did this happen' from traces alone, you are not instrumented.*" (`manifesto-principles.md` §9). `openspec/specs/telemetry/spec.md` "Privacy-preserving event design" forbids transmitting arguments, file paths, project names, spec content, or error messages, so the only runtime data is the command name. The archive (`openspec/specs/cli-archive/spec.md`) answers "why was this *change* proposed", not "why did the *agent* act". This is absent against EU AI Act Art. 12 (record-keeping) and Art. 13 (transparency) for high-risk insurance underwriting agents at Allianz.
- "Instrument decisions, tool calls, policy violations, memory retrievals, cost per task, and near-misses" (`manifesto-principles.md` §9). No file in `OpenSpec/openspec/specs/` defines a decision log, tool-call log, policy-violation feed, memory-retrieval trace, cost counter, or near-miss register. This is absent against DORA Art. 11(1) (continuous monitoring of ICT systems) and Art. 12 (backup, recovery, business continuity which require operational telemetry) for Allianz's DORA-scope agents.
- "Every agent action must produce an inspectable trace: diffs, tool calls, decision chains, evaluation results, rollbacks." (`manifesto-principles.md` §9). `openspec/specs/cli-archive/spec.md` records diffs at the *spec-Markdown* level, not at the *agent action* level; tool calls, decision chains, and rollbacks are not captured anywhere in `OpenSpec/openspec/specs/`. This is absent against Solvency II Art. 121 (statistical quality standards) which requires that the data underlying the model's decisions be auditable for Allianz's internal-model agents.
- "Traces are not logging. Logging records events. Traces reconstruct reasoning — the full chain from specification to decision to action to outcome." (`manifesto-principles.md` §9). `openspec/specs/telemetry/spec.md` emits one logging event per CLI invocation with command-name only and is convention-not-trace. This fails SR 11-7 §IV.A (model documentation must be sufficient for an independent party to understand the model's operation) for Allianz's US-regulated entities.
- "*If tools cannot be swapped or replayed across runtimes without rewriting core workflows, the platform is brittle.*" (`manifesto-principles.md` §9 interoperability bar). OpenSpec uses PostHog with `flushAt: 1` (`openspec/specs/telemetry/spec.md` Requirement: "Immediate event sending"); there is no OpenTelemetry span, no W3C Trace Context, and no OTLP exporter. This is absent against DORA Art. 6(8) (mapping ICT third-party providers and ICT services), since the platform-lock-in to PostHog is the only available trace export.
- "Stale artefacts in active evidence bundles, surfaced without manual audit using the freshness rules in the Definition of Done" (`manifesto-principles.md` §9 governance-state bar). OpenSpec has no evidence-bundle construct and no freshness rule under `OpenSpec/openspec/specs/`. This is absent against EU AI Act Art. 9 (risk management system) and Art. 17 (quality management system) for Allianz's high-risk agents.
- "Accountability ownership gaps — active production components with no named, current owner" and "rubber-stamping patterns — review-time distribution anomalies and approval-without-trace events as defined in the accountability metrics" (`manifesto-principles.md` §9). OpenSpec has no agent-inventory artefact (counterpart to `operational-templates/agent-inventory-schema.md`) and no override-rate or reviewer-agreement instrumentation (counterpart to `adoption/metrics.md`). This is absent against Solvency II Art. 41 (general governance requirements — clear allocation of responsibilities) and Art. 48 (actuarial function — independent challenge with documented rationale).
- "Model, prompt, or tool manifest changes that have not triggered an evaluation re-run" (`manifesto-principles.md` §9). OpenSpec has no foundation-model identifier, no system-prompt hash, and no tool manifest under `OpenSpec/openspec/specs/`. `openspec/specs/cli-archive/spec.md` archives on Markdown well-formedness alone. This is absent against EU AI Act Art. 15 (accuracy, robustness, cybersecurity) which requires re-evaluation when the substrate changes for Allianz's high-risk insurance agents.

## Allianz-specific implications

- EU AI Act Art. 12 (automatic recording of events — "logs") requires high-risk AI systems to "automatically record events ('logs') over their lifetime" sufficient to ensure traceability, and Art. 13 (transparency) requires operation that is sufficiently transparent to enable users to interpret outputs. OpenSpec's `command_executed` event (`openspec/specs/telemetry/spec.md`) carries only command name and version and is structurally unable to satisfy Art. 12. Allianz MUST replace OpenSpec's telemetry layer with an OpenTelemetry-instrumented agent runtime that records per-action tool calls, retrievals, and decisions to an immutable log store, retained per Art. 12's lifetime obligation, before any underwriting or claims-handling agent enters Allianz production.
- DORA Art. 9 (protection and prevention) and Art. 10 (detection) require continuous monitoring with the ability to detect anomalies promptly. OpenSpec contains no anomaly-detection construct in `OpenSpec/openspec/specs/`; PostHog "Silent failure handling" (`openspec/specs/telemetry/spec.md`) suppresses telemetry-side errors. Allianz MUST instrument every DORA-scope agent with synchronous OpenTelemetry spans exporting to the institutional SOC and wire MTTD ≤ 4 hours (per `operational-templates/slo-table.md` SLO 23) into a blocking gate outside the OpenSpec archive flow.
- Solvency II Art. 121 (statistical quality standards) and Art. 124 (validation standards) require that the data and decisions underlying the internal model be auditable by qualified independent persons. OpenSpec's archive (`openspec/specs/cli-archive/spec.md`) records spec-level Markdown changes but no per-decision artefact; SR 11-7 §IV.A imposes the same documentation depth for US-regulated Allianz entities. Allianz MUST add an action-level audit-trail layer (per `governance/integrated-audit-trail.md` §1.1 AEM execution trace) that captures `trace_ids`, tool calls, evaluation results, rollbacks, and near-misses for every Solvency II internal-model agent action, retained for the supervisory record-keeping period.
- GDPR Art. 22 (automated individual decision-making) and Art. 5(2) (accountability principle) require that the controller demonstrate compliance and that data subjects exercise the right to obtain meaningful information about the logic involved. OpenSpec does not record retrieval claims, decision chains, or the prompt/model that produced the output; the agent cannot answer an Art. 22 explanation request from OpenSpec artefacts alone. Allianz MUST persist the full reasoning trace (claim citations, prompt-and-model hash, decision rationale) for every special-category-data decision (`domains/insurance.md` "GDPR and Special Category Data") and respond within 30 days of request per GDPR Art. 12 and `operational-templates/slo-table.md` SLO 35.
- DORA Art. 17 (ICT-related incident management process) and EU AI Act Art. 73 (serious-incident reporting, ≤ 2 days for the death/widespread-infringement category and ≤ 15 days for other High/Critical categories per `operational-templates/slo-table.md` SLO 16–17) require post-hoc reconstruction of the incident's causal chain. OpenSpec records no per-action causal chain; the institution cannot reconstruct an agent-driven incident from `openspec/specs/cli-archive/spec.md` artefacts. Allianz MUST stand up a separate runtime trace store (OpenTelemetry-compatible per `governance/integrated-audit-trail.md` §1.1) for every Allianz agent product before relying on OpenSpec for any change-management role on those products.

The aggregate result is a framework whose observability covers neither reasoning nor execution in the manifesto's sense, fails EU AI Act Art. 12 / 13 / 15, DORA Art. 9 / 10 / 11 / 17, Solvency II Art. 121 / 124, SR 11-7 §IV.A, and GDPR Art. 22 / 5(2) for Allianz, and lands in the Critical band.
